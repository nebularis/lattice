## Recording what we learn

A learning left in a commit message is lost: 22 of this project's learnings existed only in git history when the index was built, including a Windows newline translation that silently corrupted generated SPARQL and two merge resolutions that made a task skip test modules without failing. The index is built as [ADR-A134](../../../docs/architecture/decisions/ADR-A134-knowledge-index-and-design-shape-vocabulary.md) says.

These rows are LATTICE's.

| What was learned | Goes in |
|---|---|
| what a store, tool, engine or platform actually does, found by probing or being surprised | [`docs/architecture/triple-store-discovery.md`](../../../docs/architecture/triple-store-discovery.md) as the next `TSD-`*n*, for a store. Otherwise the unit's status record until a register owns it |
| a facet value an entry needs and the scheme lacks | a project facets file named by `facets` in `vyvid.toml`, as a row with Ratified no, or Вивід's general scheme through its side. Tag the entry with it in the same change |
| a rule a skill states, so the index can rank it | the standard register, as a row whose Pointer is the skill's section, with Ratified no |

The row for an answer found by falling back from the index is STD-272. For a store, the next row of the discovery record is the next `TSD-`*n*.

**A register's header is a title, its Unit type line and at most one line of state.** A column's meaning is the `rdfs:comment` of the T-Box property it maps to, written once, so a header explaining its columns restates it. `check:knowledge` fails a register holding a table whose first column is not `ID` or `#`.

The first takes about two seconds.

## Picking up and finishing

The work board is [ADR-A151](../../../docs/architecture/decisions/ADR-A151-the-work-board.md), plan `work-board`. A slice's state is written once, on the board of its home unit (STD-300), for example an agent that builds a CCS slice on a formal-methods branch sets the row in the CCS record, on that branch. Marking before touching is STD-301, the ladder is STD-302, the roll-up is STD-317, the slice id grammar is STD-303 with the ids `CCS-9b.3b`, `FMH-2.6d`, `AIR-S1` and `OD-DOC1`, no plan names a branch (STD-304), the register is regenerated in the same commit (STD-305), and presence is STD-306, written into `.local/agents/`. A board row in LATTICE reads `| CCS-9b.3b | aggregate bindings | building 2026-10-30, briefed 2026-10-27 | |` followed by `| CCS-9b.4 | qualifying rules | planned | CCS-9b.3 |`, the commit that set each row is read by `mise run work:board -- --commits`, and `mise run work:board -- --all`, `-- --fetch`, `-- --measure` and `-- --commits` pass the flags after the separator, with `graph:ask -- read <slice id>` printing a slice's row.

**ROADMAP.md is kept whole, section by section** (STD-307). It is the maintainer's summary, and every section is current or says why not.

| Section | Kept by | When |
|---|---|---|
| 1 the programme at a glance, 7 branches, 9 decisions waiting, 11 completed units | generated by `mise run build:roadmap`, which the post-merge hook runs on `main` | after every merge into `main`, and on demand. Never edited by hand |
| 2 how the epics depend on one another, 8 the critical path | the planner, as diagrams | when a plan's Dependencies section gains or loses a dependency between units, or a blocker on the board changes the longest chain |
| 3 the layers | the ontology author, as a diagram | when an ADR changes the substrate's import order or proposes a layer |
| 4 active epics, 6 the platform programme | the agent handing an epic or a phase off, one subsection per epic | at each handoff and each merge that moves the epic: its documents, its ADRs, what moved and what is next, in the same commit as the status record |
| 5 smaller units | nobody. It points at section 1 | never |
| 10 the maintainer's queue | the agent proposes an order at each handoff, the maintainer orders | at each handoff that changes what unblocks the most work |
| 12 observations | the agent that refreshes the roadmap | at each refresh, every observation checked and a stale one removed |

A handoff that changes a unit's state says in its report which roadmap sections it refreshed and which it left, and why. Where a hand-written section disagrees with section 1, section 1 is right and the section is refreshed.

## Merging and releasing

- **Bump with `mise run version:bump`, and know what it moves.** The substrate, the kinds in the catalogue's `[conventions.release]`, is one release, moved together and tagged once as `ontologies-vX.Y.Z` (ADR-A129). A standalone module (MORK, SPC, Surface, Persistence) and an applied module are each released on their own, with `--layer-target <module>`: all of the module's spec documents move to one number together (STD-230), its vocab documents are a unit of their own (STD-222), its shapes share one `.version` (`--with-shapes`, `--only-shapes`), and each document that moved is tagged `<name>-vX.Y.Z` (ADR-A86, ADR-A129's addendum of 2026-10-26). `mise run check:ontology-versioning -- --base-ref main` prints a `HOW` line with the command for each module it flags, and `tools/bump_version.py` holds the mechanics (CAP-105). The per-module substrate tags from before release 0.18.0 are history.

The version rules above hold in LATTICE through `mise run version:bump` and `release:prepare`: it moves every release member's shared version number forward (ADR-A129) and cascades into every applied module that pins it, and the skill `lattice-ontology-authoring` has the rest. `check:ontology-versioning` reports a pending bump for a branch's own changed content. Where a branch defers versioning, `check:ontology-versioning`'s `UNBUMPED` is expected, the release note goes under `- **Unreleased**.` in the layer's README, classed as the versioning policy says (STD-293), and the bump is made by `mise run version:bump`, for the substrate or with `--layer-target` for a module released on its own, as the check's `HOW` line says.

Whenever `mise run build:ontology-releases` adds a row, or `mise run check:ontology-versioning` lists pending tags, end the handoff with the release tags notice.

A hook runs quick checks only (ADR-A133 decision 13, STD-318). The suites are `mise run check:persistence-conformance`, which runs the generated SPARQL on every engine we have (skill `lattice-testing`), for a change to persistence, and `mise run test:config-studio-browser`, the studio's browser suites on the fake service and on a real stack the harness starts in isolation, for a change to the studio's application, services, contracts or worker. A failure on one engine is recorded in the triple-store record.

The merge gate is ADR-A133, with published decisions over the whole tree and ontology versioning among the merge checks. A README migrated to the ADR-A126 layout may cite only a published decision (ADR-A127), and the published-decisions check fails the merge on a citation of a Proposed one, so the handoff before a merge lists every Proposed decision such a README cites under 🔴 PLAN FIRST, for the maintainer to accept first (PDD-16).
