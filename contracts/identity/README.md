# Identity Minting Contracts

The public contract between whoever produces a minting recipe (the LATTICE persistence compiler) and whoever mints IRIs from it: the LATTICE minting libraries, or your own implementation. Everything here is usable without any LATTICE code.

The normative rules are in the [identity minting specification](../../docs/architecture/identity-minting-specification.md). This directory holds the machine-readable parts.

| File | What it is |
|---|---|
| [`recipe.schema.json`](recipe.schema.json) | JSON Schema (2020-12) for a recipe: one branch per identity strategy |
| [`vectors.schema.json`](vectors.schema.json) | JSON Schema for a conformance vectors document: the embedded recipe, test secrets, positive vectors with a full trace, negative vectors with a named error, format vectors |
| [`anchors.schema.json`](anchors.schema.json) | JSON Schema for the anchor file, a list of vectors documents |
| [`anchor-vectors.json`](anchor-vectors.json) | Hand-authored anchor vectors: one set per strategy, including the published examples of the RDF and SPARQL patterns guide (the SKU of Chapter 5, the email claim of §6.1) |
| [`verify-anchors.py`](verify-anchors.py) | Recomputes every anchor byte with `openssl` and the Python standard library. Shares no code with any minting library |

## Checking the anchors

```bash
mise run check:minting-anchors
```

Or, without `mise`, from this directory with any Python 3 and any `openssl`:

```bash
python3 verify-anchors.py
```

It prints one line per failure and a summary, and exits non-zero on any failure. It verifies everything from the normalized key components onwards: recipe digests, tuple bytes, digests and MACs, truncation, encodings and rendered IRIs. The normalization steps themselves are justified by the Unicode 16.0.0 lines each anchor cites. A minter proves those by passing the vectors.

## Why the anchors exist

Vectors generated by one minting library can only show that other implementations agree with it. If that library were wrong, every implementation checked against it would be wrong the same way. The anchors are computed independently, so they are the check on the reference implementation itself. A conformant implementation passes the anchors **and** the generated vectors for each recipe it serves.

## Test secret

The claim vectors use a published test secret, stored in each vectors document under `testSecrets` and labelled as such. It exists only so that anyone can reproduce the claim IRIs. Never use it, or any value derived from it, in production.

## Content-addressed identity

The content-addressed vectors start from canonical N-Quads that are already canonical. They test hashing, not canonicalization. If you mint content-addressed identifiers, read the caller's obligations in [§7 of the specification](../../docs/architecture/identity-minting-specification.md#7-content-addressed-identity-the-callers-obligations) first: two callers who canonicalize differently mint different IRIs, and no vector can detect it.
