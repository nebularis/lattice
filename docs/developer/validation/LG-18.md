# Validation Pack: Ledger LG-18, one writer per ledger and the readings of a late posting

**Unit:** `ledger` ([plan](../plans/ledger.md), [status](../status/ledger.md)). **Builds on:** LG-17 ([its pack](LG-17.md)). **Decisions:** LG-Q9 (a), LG-Q23, LG-Q26, ADR-A124, PDD-14, STD-278, STD-294. **Findings:** TSD-73, TSD-74. **Debt:** TD-162.

## Invariant

One writer fed through a queue leaves records equal to the replay of its commits, with dense revisions, on every store measured, whether it reads its path for every posting, keeps the balances it has settled, or writes several postings in one update. A reading of a balance for a day as known at a recording equals the model for each of the three readings of LG-Q26, is the same from a store that holds only what was recorded by then, and for the recorded amounts equals the ledger's balance where the day is the recording's own.

## One command

```bash
mise run check:ledger-credit-kinds-single-writer
mise run check:ledger-credit-kinds-late-readings
mise run check:ledger-credit-kinds-jvm-writes
```

`LEDGER_WRITES_QUICK=1` runs the smallest sizes of each. The first runs the 14 cases of `test_single_writer.py`, then the guarded writers, the closed runs and the backlog on Oxigraph in memory and on disk and on Jena through the test kit. The second runs the 6 tests of `test_late_readings.py`, then the readings at 5,000 and 20,000 postings with none, 5% and 20% of the postings late. The third is LG-17's native task, which now also runs the queue on Jena in memory and on TDB2. Each runs on demand, is never part of `check`, and fails on a wrong result and never on time (ADR-A124).

## Deliberate non-coverage

A store that takes concurrent writers and holds the guard at a higher rate than one writer, which is what a backend such as a property graph store with snapshot isolation might be. The guarded writers are run beside the single writer so the two can be compared on the stores here, and no such store is among them. Several ledgers written at once, which is where a single writer per ledger scales and where Jena's one writer per dataset would not. A writer that survives a restart, since the keeper's balances are rebuilt by reading them again. Requests that arrive at a rate, as against a closed loop and a backlog. Writes over HTTP or from several processes. For the readings, any store but Oxigraph in memory, a checkpoint that carries the flow totals, and which reading a report should show, which is LG-Q26.

`WRONG RESULT` on standard error with a non-zero exit is a failure of the benchmark's pass criterion, and its message names the read. A test that passes where its row above says it must raise is a test that cannot fail, and is to be made to.

**Where a first run is most likely to fail**, since none of this has run. The Java, on a compile error. `test_sw4`, if the second seeded request is a debit the keeper refuses, so that nothing is written. `test_lr5`, if no ancestor's reading B depends on the order at 1,000 postings. The checkpointed reading A, if a checkpoint's balance is not the sum with cuts at its close. The test kit's Jena, if it does not accept calls from a thread other than the one that made it.

**What we expect, to be tested.** From LG-17's figures on a laptop, a single writer that reads its path serves about 300 postings a second on Oxigraph in memory, 90 to 140 on disk, 100 to 200 on Jena in memory and 9 on TDB2. Planned at 70% of that, one ledger takes about 18 million postings a day on Oxigraph in memory and about half a million on TDB2. A keeper should reach some thousands a second in memory, and on TDB2 about 10 a second until it batches, then roughly the batch size times that. The limit is for one ledger. Ledgers do not share a writer, so they add up on a store that writes them side by side, and do not on Jena, where a dataset has one writer.
