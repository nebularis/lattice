# Validation Pack: FMH-H1.3, static template checks S-3 and S-4

**Unit:** [`formal-methods-track-h`](../status/formal-methods-track-h.md), slice H1.3
([plan §3, H1.3](../plans/formal-methods-track-h.md))
**Source finding:** [review](../notes/rdf-engine/persistence-fml.md) §12, S-3 and S-4, the two checks
the review would implement first.
**Decisions:** none ratified. Two interpretations are recorded as H-D11 and H-D12 for the human.

## Invariant

Every update the compiler generates is statically free of two defects.

- **S-3.** A variable in an INSERT template that is not bound in every solution makes the engine skip
  that triple silently, so a record can lose a field with no error. Each INSERT variable must be a
  request-time `$parameter`, bound in every solution of the WHERE clause, or listed with a reason in
  a reviewed allowance.
- **S-4.** A blank node in an INSERT template is fresh on every solution and every execution, so a
  retry is not a no-op. In a DELETE template it is not legal. Neither may appear.

## What changed

- `persistence/templatecheck.py` (new). It renders each generated operation as `instantiate` does,
  parses it with rdflib, and analyses the algebra. Which variables are bound in every solution is
  worked out conservatively from the WHERE clause (`OPTIONAL` and one-sided `UNION` do not bind,
  `VALUES` binds unless a row is `UNDEF`, a group-by sub-select binds its keys and aggregates). A
  construct it cannot analyse is reported, never passed over. A read-only audit query has no
  template and is skipped.
- `python -m persistence hygiene` now also compiles the configuration and runs the two checks over
  its generated operations. If the configuration does not compile it says the templates were not
  checked.
- Two fixtures, `template-append-event.ttl` and
  `template-cas-replace-composite-property-dataset-guard.ttl`, because **three of the 24 templates were
  never generated by any shipped example** (`append-event`, `bootstrap-version-row`,
  `cas-replace-composite-property-dataset-guard`) and so no check could have seen them. A test now
  requires every template in the library to be generated by some fixture.

## Result on the real templates

| Check | Result |
|---|---|
| S-4, blank nodes | none in any INSERT or DELETE template |
| S-3, unbound INSERT variables | one variable in 8 templates, the **previous revision** |
| Not parseable, or not analysable | none |

The previous revision is `?prevRev` in the CAS, composite CAS and tombstone templates (six files with
their dataset-guard variants) and `?prev` in the two append templates. Each is unbound on the first
write to a pre-created row or a new stream, because there is no `pat:head` yet, and the `pat:prevRev`
triple is correctly absent. The templates' own comments say so. Each is recorded as an allowance with
that reason. The allowances are checked for staleness across the whole corpus, so one cannot outlive
the variable it excuses.

**No defect was found in the templates.** The checks did what the review hoped for them, and the
value so far is a standing guard. The review's two examples of what they would have caught are already
fixed.

## Decisions for the human

| # | Decision |
|---|---|
| H-D11 | The `$name` convention marks a request-time parameter, so such a variable is treated as bound. The compiled profile lists no request-time parameters (all its bindings are compile-time), so the convention is read from the text. The alternative is to have the compiler emit the parameter list, which is a change to its output. |
| H-D12 | A `BIND` over bound inputs counts as binding its variable, though an expression can raise an error and leave it unbound. Treating every `BIND` as unreliable would flag nearly every template. |

## Deliberate non-coverage

- Blank nodes in the caller's payload. Generated operations take a skolemized payload (guide §15.2), so
  that is the caller's obligation, and the payload slot is replaced by a ground triple here.
- That a `$parameter` is actually supplied by the caller. That belongs with the obligation set for
  each operation (review PV-D2).
- Whether the data an INSERT writes is the data the audits and reads expect. H9.
- Templates for dialects the compiler does not generate, and constructs rdflib cannot parse.
