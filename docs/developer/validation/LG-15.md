# Validation Pack: Ledger LG-15, the credit kinds benchmark's gaps closed

**Unit:** `ledger` ([plan](../plans/ledger.md), [status](../status/ledger.md)). **Builds on:** LG-14 ([its pack](LG-14.md)). **Decisions:** LG-Q10, LG-Q9 (a), ADR-A124, STD-155, STD-176, STD-324. **Findings:** TSD-71, TSD-72.

## Invariant

LG-14's read costs are known without the gaps its pack listed: Jena called natively, in memory and on TDB2, reads that start from a checkpoint at each close, a credit clamped at the account it is posted to as well as at the ancestor, the stepwise loop timed apart from its query and transfer, and a shortcut that sums and falls back to the stepwise fold only where a sum could be wrong. Every read on every engine equals the model.

## Handoff

Built 2026-11-11 on machine R by a Sonnet subagent, checked here with both quick runs the same day: the Python task 37 passed and every read on rdflib 7.6.0, pyoxigraph 0.5.13 and Jena ARQ 5.1.0 equal to the model, exit 0, and the JVM task 4 passed and native reads on Jena in memory and TDB2, exit 0. The subagent's full runs passed, the Python task in about 14.5 minutes and the JVM task in 72 seconds.

Time of the 27 ancestor reads against the plain fold, 30% credits, from the start of history, for 1,000 / 5,000 / 20,000 postings:

| Backend | kind-filtered | stepwise |
|---|---|---|
| rdflib | 1.8 / 1.7 / 1.2 | 1.8 / 1.8 / 1.3 |
| Oxigraph | 2.0 / 2.1 / 2.1 | 4.7 / 5.1 / 5.2 |
| Jena through the test kit | 1.3 / 1.4 / 1.4 | 4.4 / 5.3 / 5.3 |
| Jena in memory, native | 1.5 / 1.3 / 1.4 | 1.9 / 2.4 / 2.6 |
| Jena TDB2, native | 1.3 / 1.3 / 1.4 | 1.7 / 1.8 / 2.0 |

The stepwise read now joins each credit's applied amount, which is why its factors rose from LG-14's on Oxigraph and the test kit. The loop itself costs at most about a millisecond at 20,000 postings on every engine, so the stepwise cost is the engine's ordered query. Natively, Jena's transfer into Java is 2 to 3 ms.

**Checkpoints.** A read from the last checkpoint costs 0.02 to 0.05 of a read from the start, on every engine and fold, the root folding 244 rows instead of 11,358, except the stepwise read on Oxigraph, which costs 0.92: its `OPTIONAL` join to the applied amount appears to scan as TSD-71's `OPTIONAL` join does, which was neither confirmed from a plan nor tried in a `UNION` form.

**The shortcut** falls back on every read from the start of history and on 18 to 26 of 27 checkpointed reads at 30% credits, and costs 1.4 to 2.7 times the stepwise fold except on Oxigraph at 5% credits from a checkpoint, where it costs 0.03 s against 3.43 s.

**The corrected `UNION`** keeps credits with no kind by a third branch, costs 0.2 to 0.4 of the plain read more than before, and leaves each engine's cheaper form unchanged, `OPTIONAL` on rdflib and Jena, `UNION` on Oxigraph.

**A finding for the design.** Once a credit is clamped at the account it is posted to and an ancestor folds the applied amount, no ancestor's ceiling bound in the corpus at either credit share, and the subagent showed why: an ancestor's outstanding draw is at least the sum of its contracts', and a kind filter only removes credits. That holds where every ceiling equals its account's stated amount, as in this corpus. The ledger lets a ceiling stand above the stated amount (`ldg:CreditCeilingNotBelowStatedShape`), and there an ancestor's ceiling can still bind. So where a credit records the amount it was applied at, an ancestor's balance is a plain or kind-filtered sum under that condition, which is LG-Q23.

**Deliberate non-coverage.** Query plans, so the cause of TSD-71 and of the Oxigraph checkpoint read is not known. RDF4J and Fuseki. A ceiling above the stated amount. The JVM reads include some JIT warm-up at the smallest size.
