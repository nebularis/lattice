# Validation Pack: LG-36, the kernel's code equations in a theory of their own

**Unit:** `ledger` ([plan](../plans/ledger.md), LG-36, [status](../status/ledger.md)).
**Placement:** T0, public substrate.
**Decisions:** none. [ADR-A-FM2](../../architecture/decisions/ADR-A-FM2-formal-methods-theory-home.md) places the theories, and no decision record was edited.

**Status:** built 2026-11-25, awaiting the maintainer's verification.

## Invariant

A split, a merge and a draw up an account's path evaluate on `Kernel.thy` and `Evaluation.thy` alone, in a session whose parent is HOL, with no library theory. The session `Ledger` proves what it proved before, with the same 83 claims.

## What changed

- **A new theory.** [`tools/proofs/ledger/Evaluation.thy`](../../../tools/proofs/ledger/Evaluation.thy) imports `Kernel` alone and holds `inj_on_code` and `path_step`, each word for word as it was, and three examples proved by `code_simp`.
- **`Allocation.thy`** imports `Evaluation` where it imported `Kernel`, and no longer states `inj_on_code`.
- **`Draws.thy`** no longer states `path_step`. It reaches it through `Allocation`. It still imports `HOL-Library.Multiset`, for its own theorems.
- **`ROOT`** names `Evaluation` after `Kernel`.
- **The proofs' [README](../../../tools/proofs/ledger/README.md)** lists the theory and names the lemma as `Evaluation.path_step`.

`Kernel.thy` is unchanged, so the layer's README and its extracted documents are unchanged. No claim names either lemma, so no claim file changed. [LG-9's pack](LG-9.md) names the lemma as `Draws.path_step`, which was its name when that pack was written.

## Probes

- **The path's equation is what makes a draw evaluate.** In a copy outside the repository, `lemma path_step [code]:` became `lemma path_step:`. The build failed with `Wellsortedness error: Type nat not of sort {enum,equal}` at the `by` of `example_a_draw_up_a_path`. With the copy restored it built.
- **The injectivity equation is needed by no evaluation.** In the same copy, `lemma inj_on_code [code]:` became `lemma inj_on_code:`, and the build still passed. The session `Ledger` was then built once with the same change to the tracked file, and it finished in 21 seconds with no error, after which the file was restored from a copy and the gate run again. HOL's definition of injectivity on a finite set evaluates by comparing every pair of keys, so the equation changes the cost and not the result. `example_an_order_checked` therefore shows that a merge which checks its order evaluates on the two theories, and does not hold the equation in place.

## Artefacts to inspect

`tools/proofs/ledger/Evaluation.thy`, the first lines of `Allocation.thy` and of `Draws.thy`, `tools/proofs/ledger/ROOT`, and the theory table of `tools/proofs/ledger/README.md`.

## Deliberate non-coverage

- No task builds the two theories on HOL alone. The verification rig's projection P2 will, once it reads the kernel, which is that unit's slice.
- No test holds `inj_on_code` in place, as the second probe shows. Whether to keep it for its cost on a large set of keys, or remove it, is not decided.
- The cost of evaluating a path or a merge is not measured.
- LG-35 changes the kernel again. The examples here use `proportional`, `draw_on`, `path`, `available` and `merge_of`, and would be restated with it if it renames any.
