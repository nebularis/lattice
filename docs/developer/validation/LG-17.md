# Validation Pack: Ledger LG-17, what LG-16 left open

**Unit:** `ledger` ([plan](../plans/ledger.md), [status](../status/ledger.md)). **Builds on:** LG-16 ([its pack](LG-16.md)). **Decisions:** LG-Q10, LG-Q9 (a), LG-Q23, ADR-A124, STD-155, STD-176. **Findings:** TSD-71, TSD-72.

## Invariant

On the two-level corpus every read form (the plain fold, the shortcut, a kind-filtered read in the sum with cuts' own `UNION` form, and the sum with cuts) equals the model at every ancestor, read point and mode on every engine, and the sum with cuts equals the stepwise balance. A cut that copies its position gives the same balances as the joined cut. Where a ceiling is above a stated amount, the writer, the model and the stepwise read clamp at the ceiling, and the sum with cuts is still the stepwise balance. The sketch's tree and history, loaded into an engine, read the sketch's figures. Part two adds the live writer. Its records, written with the guard of one revision triple, equal the replay of its commits through the benchmark's writer, in fixed interleavings and in a stress of threads against one in-memory Oxigraph store, whose revisions are dense, while the same writer without the guard does not. The recorded sum equals the stepwise replay where postings are recorded after they take effect, and the effective sum, folded from the start, equals the model. Part three reads the two-level corpus from Java on Jena in memory and on TDB2, by the plain, kind-filtered, `kind-filtered-union`, stepwise and sum-with-cuts folds, and each equals the model, as does the sum of applied amounts the postings alone give. It runs the live writer from Java against both Jena stores, with a counter probe of what each store does with concurrent guarded updates, and each export is replayed by the Python audit, which is held to the guard only on a store whose probe kept it.

mise run check:ledger-credit-kinds
mise run check:ledger-credit-kinds-writes
mise run check:ledger-credit-kinds-jvm

`LEDGER_KINDS_QUICK=1` runs the smallest size, and `LEDGER_KINDS_NEW_ONLY=1` skips the one-level corpus and runs only what LG-17 added. The first task runs the tests (82), then the one-level corpus, the two-level corpus with its like-for-like reads, the cut forms and the ceiling variant. The second runs the write tests (20), then the live writer, the interleavings, the stress and the late postings, and takes about 7 minutes. `LEDGER_WRITES_QUICK=1` runs the smallest sizes. The third runs the 16 tests of the Java read run, writes the two corpora and their expected values, reads both from Java on Jena in memory and on TDB2, writes the plans of three reads, and merges the timings into the first task's report. The fourth runs the 6 tests of the Java write run, writes the preloads and request lists, runs the probe, the single writer and the stress from Java, exports each store, audits the exports in Python and writes `writes-report.md`. Each says in its description that it runs on demand, is never part of `check`, and fails on a wrong result and never on time (ADR-A124).

## Deliberate non-coverage

Writes over HTTP or from several processes, a store other than Oxigraph under concurrent writers, a writer that writes a checkpoint at a period close, a guard narrower than the owner's ledger, and any rule that consumes an amount in effective order. On-disk Oxigraph is audited and not asserted. A query plan for an engine other than Jena, since the Oxigraph Python binding and rdflib offer none to read, and for Jena the execution log, which goes to a no-op logger, so the plans are the algebra and the order the store's reordering gives and carry no counts or times. The native caller does not read the ceiling variant, the cut forms or the shortcut on the two-level corpus. The native writers are threads in one JVM, not several processes or HTTP, and on TDB2 they run at smaller counts than the Python benchmark and Jena in memory, because each commit is made durable. A store other than Jena for the native writer. A ceiling that moves in time. The ceiling variant is read at 30% credits only and without the plain fold or the shortcut. The shortcut's soundness on the two-level corpus is checked by the model comparison of every read and not proved.

## Handoff

### Part one, read forms and storage

Built 2026-11-12 on machine R and reviewed the same day, when the 82 tests were run again (82 passed in 158 s, exit 0) and the report and the change were read in full.

**What was built.** The two-level corpus gains, under `like_for_like`, the plain fold, the shortcut and `kind-filtered-union`, the kind-filtered sum of offered amounts in the three-branch `UNION` form of the postings part of the sum with cuts. The shortcut's check counts, on this corpus, the credits posted anywhere in the read account's subtree against what each account on the path has outstanding, since a credit at an internal account restores every accepting account above it. The one-level check is unchanged. A cut has a named storage choice, `cut_form`, `joined` (3 triples, the default) or `copied` (4, with `l:cutPosition`), and `run_backend_cut_forms` loads each into its own store and reads the sum with cuts from the start and the checkpoint. An account has a `ceiling_amount` and a `ceiling`, which is the stated amount unless set, the writer, the model, the stepwise read and the shortcut's check use the ceiling, and `l:ceilingAmount` is stored only where set, so every default count is unchanged. `build_ceiling_tree` gives 11 of the 30 contracts and sublimits a ceiling of 1.5 times their stated amount, and `run_backend_cuts(..., ceiling=True)` reads the variant. `using_tree` runs the benchmark's functions on another tree, and `run_sketch` loads the sketch's four-step history into each backend and reads every fold. The environment switch `LEDGER_KINDS_NEW_ONLY=1` is documented in the task's description.

### Part two, writes, concurrent writers and late postings

Built 2026-11-12 on machine R.

**What was built.** `writes.py` holds a live writer. For one posting it reads the ledger's revision and the sum with cuts of every account on the path from the last checkpoint (a contract has its own read), settles with `settle_debit` and `settle_credit`, refuses a debit larger than the balance of any account on its path, and writes the posting, its applied amount, kind and cuts and the new revision in one update. The guard is `DELETE { revision N } INSERT { revision N+1 and the posting } WHERE { revision N }` (PAT-21, PAT-04), and the committed revision is the posting's recorded position. The writer confirms by asking for its own posting, whose IRI is unique to the writer and attempt. The unguarded writer sends `DELETE DATA ; INSERT DATA` and does not confirm. `audit` reads every record back and compares it with the replay of the whole history through the benchmark's writer, and checks the revisions are dense. The stress runs threads against one store, each with its own seeded requests. A late posting is stored in the period graph of its recorded position with its effective position as one more triple, a choice of the benchmark and not a decision (PDD-14 is open). `run_late` compares the recorded sum, the effective sum (folded from the start, STD-278) and two replays. The writer writes no checkpoint, so its reads fold every period after the last one. `check.py` is unchanged.

### Part three, the native Jena caller

Built 2026-11-12 on machine R and reviewed the same day, when the 124 tests were run again (124 passed in 238.02 s, exit 0), the two reports, the plans file and the three Java classes were read in full, and the counter probe was repeated by a second program written apart from the benchmark, which kept the guard in 9 of 9 runs on Jena in memory and 9 of 9 on TDB2. What Jena does with concurrent writers is recorded as TSD-74.

**What was built.** `check.py --emit` also writes the two-level corpus of each size and share and, for each ancestor, read point and mode, the model's balance and posting count for the plain, kind-filtered, `kind-filtered-union`, stepwise and sum-with-cuts folds, with the model's sum of applied amounts and stepwise balance for the sum with cuts. The `emit` function does this only when asked (`two_level`), so its one-level use and its test are unchanged. The Java module reads both corpora on Jena in memory and on TDB2 and checks every value, including that the postings alone differ from the stepwise balance at as many ancestors as the model says. The two-level corpus is read in the `optional` kind join form, `-Dkinds.forms2` adds `union`, and the shortcut is not read on it. `--merge` adds a section "Native Jena (Java), two-level corpus" with the Python callers' tables and the five folds side by side. `Plans.java` writes, to the module's git-ignored `target/plans.txt`, the algebra as compiled and as optimised by ARQ for three reads of the root at the largest size and 30% credits, and for TDB2 the quad form and the order the store's reordering gives. The execution log goes to a no-op logger, so it is not read. `LedgerWrites.java` ports the live writer, runs the counter probe, the single writer and the stress against both stores, and exports each store as gzipped N-Quads. `writes.py --emit-jvm` writes the tree, the preloads and the request lists, `--audit-jvm` loads each export into an in-memory Oxigraph and runs `audit`, strictly for a guarded run on a store whose probe kept the guard in every guarded run at two threads or more, and for a single writer's guarded run, and never for an unguarded run. Choices the brief left open were that a write reads its path in one read transaction, that TDB2 runs smaller counts because each of its commits takes 84 to 98 ms (the probe to 100 markers and 50 increments, the single writer for 100 writes, the stress for 200 requests, each cell three times at 2, 4 and 8 threads, where Jena in memory runs 1,000 markers, 500 increments, 500 writes and 1,000 requests), that a warm-up writer runs first, and that the audit's strictness is decided in Python from the Java report.
