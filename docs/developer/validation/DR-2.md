# Validation Pack: DR-2, the bulk load and the recorded state digest

**Unit:** [`persistence-delta-replace`](../status/persistence-delta-replace.md), slice DR-2 of the [plan](../plans/persistence-delta-replace.md), built on 2026-11-01 in autonomous mode. Versions are deferred to the merge (STD-111).

**For the maintainer:** read the decisions taken alone below, which shape both features. **For countersignature (non-weakening rule):** no test was weakened. Two counts grew by the new builders, and the alignment test that holds every write of a transaction claim to record its request digest leaves out `record-state-digest`, which reads the claim and writes none.

## Invariant

A bulk load of many aggregates' whole states is one request in which each aggregate is created if it has no row and replaced if its row is at the sequence the caller read, and an aggregate whose row moved is left as it was (DR-Q6 (a)). A family that declares `dal:recordsStateDigest` can record, in the same request as each write, the digest of the state the write left, and an audit recomputes it and finds a graph changed outside the family's operations (DR-Q3 (c)).

## What changed

- **Vocabulary.** `dal:recordsStateDigest`, the operation kinds `dal:StateDigestRecord` and `dal:StateDigestRead`, and the store term `pat:stateDigest`, in the persistence README (§5.6.12) and the patterns guide's Appendix A.
- **Operations.** Under `dal:ChangedTriples` a family also has `replace-whole`, its whole replace. Under `dal:recordsStateDigest` it has `record-state-digest`, and `state-digest-audit-named-graph` or `state-digest-audit-composite`.
- **Libraries.** `compose` in both, which joins filled operations into one request with one prologue, and `state_digest` (`RequestDigest.stateDigest` in Java), the digest of a state's sorted canonical N-Triples.
- **Store finding.** TSD-68: Oxigraph refuses a prologue after `;`, so `compose` hoists the prologues.
- **Witnesses.** `template-record-state-digest.ttl` and `template-state-digest-audit-composite.ttl`, so every builder is generated by a fixture.

## Decisions taken alone, for the maintainer's review

1. **A bulk load is composed by the caller, not generated as one operation.** Each aggregate's payload is its own slot, and one template cannot hold a variable number of them. The caller sends, for each aggregate, its create and its `replace-whole` under one transaction id, so whichever half applies claims the transaction and the other finds the claim and does nothing.
2. **The state digest is recorded by a separate operation in the same request,** not by a variant of every create and replace, which would have doubled the builders for an option that is off by default. It applies only after its write, by the row's sequence, the row being live, and the transaction's claim.
3. **The state digest is the request digest's encoding over the state's lines alone,** with no kind, target or sequence, so it is a function of the state and nothing else.
4. **The audit returns the recorded digest and the aggregate's triples, and the caller compares.** SPARQL cannot compute the digest, so the store cannot.
5. **`replace-whole` is generated for every family under `dal:ChangedTriples`,** at the cost of one operation in its profile, so a bulk load needs no change to the profile.

## Not covered

The studio's import does not use the bulk load yet. The linear replace (LR-Q1 to LR-Q3, on its own branch) will change `replace-whole` where a store has snapshot semantics.
