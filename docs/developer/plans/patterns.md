# Pattern register

**Unit type:** [Register](../../../tools/knowledge/README.md#registers)

Handles on the sections of the RDF and IRI pattern guides, which stay the source. Not yet ratified.

| ID | Name | Claim | Cost | Shapes | Evidenced by | Pointer | Ratified |
|---|---|---|---|---|---|---|---|
| PAT-01 | P0: deterministic IRIs | **Derive an entity's IRI from a normalised, immutable natural key, so concurrent writers converge on one subject and uniqueness is structural, with no lock or isolation requirement.** | The IRI changes if the key changes, a hash of a low-entropy key is reversible and leaks it, and the hash algorithm, encoding, version and width become identity-bearing. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:432-492` | no |
| PAT-02 | 6.1 Natural-key pattern | **Mint the IRI directly from an immutable, non-sensitive key, so derivation is deterministic, idempotent and readable with no lookup.** | Changing a key changes identity, and natural keys can leak personal data, business secrets or correlation identifiers. | |  | `docs/architecture/iri-identity-patterns.md:260-270` | no |
| PAT-03 | P1: the key-claim registry | **Claim each unique key with a keyed deterministic node that has at most one owner, so uniqueness becomes a per-node cardinality check and the entity keeps a stable opaque IRI.** | Claim allocation needs a guarded write plus a concurrency mechanism suited to the backend, and convergence across environments is absent unless the claim registry is shared. | | TSD-36 | `docs/architecture/rdf-sparql-patterns-guide.md:496-578` | no |
| PAT-04 | P2: the guarded write in one request | **Take the claim and write the payload in one guarded update, so if the key is taken neither lands and an identical retry is a no-op.** | It is write-skew-prone under snapshot isolation, so two different claimants racing for an unclaimed key still need P3 or P6. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:580-626` | no |
| PAT-05 | P3: materialise the write conflict | **Force racing writers to rewrite one pre-created sentinel statement, sharded by key hash, so a store with write-write conflict detection aborts one of them.** | False conflicts between unrelated keys that hash to the same shard, and it adds contention, so it is not for high-contention keys. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:652-688` | no |
| PAT-06 | P4: upsert for functional properties | **Replace a functional property's value, retire the old claim and take the new one in a single operation, so claims never leak and no window opens in which another writer can take the key.** | A rotation is refused outright when the new key is already taken, and retiring the old claim and taking the new one must be a single operation. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:690-728` | no |
| PAT-07 | P5: SHACL as the safety net | **Use sh:maxCount 1 on the claim node as a commit-time constraint or an offline audit, turning a silent lost update into a loud error where the store validates committed state.** | Several incremental validators support only a subset of SHACL, and sh:sparql may force full-graph revalidation on every commit. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:730-765` | no |
| PAT-08 | P6: external allocator or lock | **Put uniqueness in a system with a real unique index or lock, with a fencing token, and project to RDF idempotently, for high-contention keys and non-ACID backends.** | It adds an availability and reconciliation boundary, and the RDF representation becomes a projection that must be idempotently repairable. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:767-811` | no |
| PAT-09 | P7: detect and reconcile | **Run a duplicate scan nightly or streaming into a quarantine graph, to catch what bulk loads, restores and rogue ETL bypass, with a reject, merge or quarantine policy per constraint.** | The SPARQL scan groups on the raw literal and misses normalisation-variant duplicates, so the primary reconciler is an application-side job. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:813-838` | no |
| PAT-10 | 8.3 Bulk and backfill | **Load in bulk through a separate pipeline: normalise and number offline, load into staging with validation off, gate on the gap, fork and duplicate scans, then cut over in batches.** | Cutover runs in batches with writers of the affected streams quiesced or routed to the bulk pipeline until the last batch lands. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2446-2456` | no |
| PAT-11 | S1: the in-transaction counter | **Allocate each stream position inside the writing transaction on one version-row statement, so allocation order equals commit order and the sequence is dense.** | The engine must serialise writers or detect write-write conflicts, counters must be bootstrapped eagerly, and a conflict is retried with jittered backoff. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1000-1125` | no |
| PAT-12 | S2: keyset (seek) pagination | **Page a log by seeking past the last composite position (epoch, seq, opSeq), never by OFFSET, which is O(offset) and unstable under concurrent writes.** | The client must carry the full composite position and re-read the dataset epoch before resuming, and a restore or migration invalidates every position held. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1129-1145` | no |
| PAT-13 | S3: the gap and completeness check | **Prove a consumer has lost no event by checking, per target, that retained sequence numbers are contiguous from the retention low-water mark to the version row's sequence.** | It needs a dense per-stream sequence, so it is impossible with an HLC or a store LSN. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1147-1180` | no |
| PAT-14 | S4: latest revision per stream | **Read a stream's latest revision from a materialised head pointer upserted in the write's transaction, a single-triple lookup, keeping MAX(seq) for audit only.** | Every write form must maintain the head pointer, or the other form reads a stale head and the receipt chain has holes. | | TSD-36 | `docs/architecture/rdf-sparql-patterns-guide.md:1182-1204` | no |
| PAT-15 | S5: valid-time ordering with a deterministic tiebreak | **Order domain questions by valid time with the transaction-time position as a deterministic tiebreak, never by seq or recordedAt alone.** | An event lacking opSeq is silently excluded from the result rather than sorted first or last, so a family of mixed grain needs its own query. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1206-1229` | no |
| PAT-16 | S6: as-of reads | **Reconstruct the state at a position by replaying the log's add and delete graphs, the portable form of an as-of read.** | It is expensive and grows with history depth, and replaying forward is wrong under prefix-only retention, so it is reserved for audit. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1231-1271` | no |
| PAT-17 | S7: hybrid logical clocks for the sparse tier | **Order the dataset tier by an application-computed HLC string, which is contention-free, close to wall-clock and robust to NTP step-backs.** | It gives no completeness detection, and is causally consistent only across writers that exchange HLC values. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1273-1323` | no |
| PAT-18 | S8: external sequencer or partitioned single writer | **Partition the writer by key so each stream has one writer that allocates its own dense counter and writes to RDF idempotently through an outbox, mandatory where the backend has no usable transaction.** | A dense sequence needs one serialised writer per stream and an outbox. A SQL sequence or a Kafka offset is simpler and leaves gaps and out-of-order commits. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1325-1337` | no |
| PAT-19 | O5: integer index property | **Keep an ordered collection in the data as an integer index property, which is simple, sortable and pushdown-friendly.** | Renumbering on insert. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1339-1371` | no |
| PAT-20 | O5: fractional or lexicographic ranking keys | **Keep a user-reorderable list under string ranking keys, so insertion between two items is O(1) with no renumbering and ORDER BY runs on a plain string.** | It occasionally needs a rebalance pass. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1339-1371` | no |
| PAT-21 | 14.1 The CAS primitive | **Guard a whole-graph replace on the version row's expected sequence in one DELETE/INSERT WHERE request, so a stale write is a no-op and the replace is the aggregate's complete state.** | The protocol returns 204 whether or not the write applied, so the outcome is unobservable without a separate confirmation. | | TSD-01 | `docs/architecture/rdf-sparql-patterns-guide.md:1405-1431` | no |
| PAT-22 | 14.2 Value-based CAS | **Guard on the old value instead of a version triple, for status transitions on internal nodes.** | It cannot detect that someone else changed a different field. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1433-1472` | no |
| PAT-23 | 14.2 Field-level versions | **Keep a sequence per field group on a hot aggregate, to reduce false conflicts between writers touching different parts.** | The aggregate is no longer one unit of consistency. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1433-1472` | no |
| PAT-24 | 14.2 Content-hash ETags | **Hash the payload with RDFC-1.0 instead of counting, for natural no-op detection and offline or mobile sync.** | Real CPU on large graphs, and a hash carries no order, so it cannot serve as a sequence. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1433-1472` | no |
| PAT-25 | 15.2 The receipt, then the txn claim | **Record each transaction id as a claim in a small dedicated graph, with a request digest, so a client learns definitively whether its write applied and a retry is idempotent.** | The claim protects retries only while retained, so its TTL must exceed the longest redelivery horizon, or a late retry gets a misleading 412 or applies twice. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1498-1546` | no |
| PAT-26 | 15.4 HTTP-level CAS | **Push concurrency control up to HTTP with a strong ETag and If-Match on a graph per aggregate, as LDP and Solid N3 Patch standardise.** | The Graph Store Protocol does not require If-Match, so a proxy that fronts the store may need adding. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1554-1597` | no |
| PAT-27 | 16.3 Lease or checkout locks in the graph | **Hold a lease in the graph for human-scale editorial checkout of an aggregate.** | Acquisition is still a CAS that needs another mechanism under it, and expiry needs a clock with its caveats. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1631-1642` | no |
| PAT-28 | 17 Separating metadata from payload | **Keep version metadata in a graph apart from the payload, so one small hot statement serves the counter and the CAS guard and a whole-graph replace cannot erase the ordering evidence.** | It buys no dataset-wide order, epoch safety or cross-aggregate atomicity, and a dataset-wide counter in the meta graph removes per-aggregate sharding. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:1668-1706` | no |
| PAT-29 | 20.1 Receipt-only | **Append only a revision receipt per write, for CAS outcomes, audit breadcrumbs and ordering, at the lowest cost of the three receipt models.** | It orders revisions but cannot replay them, so there is no replay or as-of. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2112-2121` | no |
| PAT-30 | 20.2 Patch log | **Record each revision's asserted and retracted delta graphs beside the receipt, computed client-side, enabling replay, as-of reads and change capture.** | About twice the write volume, and the delta graphs need bucketing discipline. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2123-2138` | no |
| PAT-31 | 20.3 Snapshot per revision | **Write each revision to a new immutable graph named by epoch and position and point the head at it, giving trivial as-of reads and immutable evidence.** | The highest storage and write amplification, and graph proliferation. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2140-2154` | no |
| PAT-32 | 21.3 Watermarked read | **Read the dataset tier only up to a watermark known to be safe, so nothing arrives out of order after the fact.** | It trades latency for the guarantee and needs a watermark source. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2196-2229` | no |
| PAT-33 | 21.3 Lag-window read | **Read the dataset tier up to now minus a fixed lag, the pragmatic default when no native watermark exists.** | A fixed delay, and the lag must come from the enforced maximum transaction duration, not observed latency, or it is a guess. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2196-2229` | no |
| PAT-34 | 21.3 Dense feed read | **Read the store's own dense change feed directly for the dataset tier, the strongest guarantee where the backend has one.** | It is the least portable option. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2196-2229` | no |
| PAT-35 | 24.1 Tombstones | **Delete an aggregate by a CAS with an empty payload and a tombstone on its version row, so the counter never resets and no revision IRI is reused.** | The version row is kept forever. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2324-2399` | no |
| PAT-36 | 24.2 Retention and pruning | **Drop whole monthly receipt buckets only as a contiguous prefix from the oldest end, advancing a low-water mark and copying live heads first.** | A stream written once and never since has its head in the oldest bucket, so live heads must be pinned by copying their receipts before each drop. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2401-2444` | no |
| PAT-37 | 10.3 Epoch durability | **Bump a durable dataset epoch on restore, rebuild or migration and compare it in every write, so positions and ETags from before cannot be mistaken for new ones.** | Every open ETag and consumer position becomes stale by construction and consumers must resynchronise. | |  | `docs/architecture/iri-identity-patterns.md:540-555` | no |
| PAT-38 | 24.5 Erasure of personal data | **Hold personal data in one aggregate per data subject, erase it by decision record with a graph drop or key destruction, and replay an external erasure register on restore.** | Backups still hold erased data until they expire, and claims over personal keys must be physically deleted, which breaks claim ownership monotonicity. | |  | `docs/architecture/rdf-sparql-patterns-guide.md:2472-2484` | no |
| PAT-39 | 5.1 Adopted or external identifiers | **Preserve an authority's already-assigned identifier as the domain identity, with a local mapping for provenance, authority and validation status.** | The source may change its identifier policy, its strings may not meet the local grammar, and foreign IRI access may be unavailable offline. | |  | `docs/architecture/iri-identity-patterns.md:144-154` | no |
| PAT-40 | 5.4 Direct identity | **Give a part its own independent entity IRI when it has a lifecycle and references outside its parent.** | It requires its own merge and authority policy. | |  | `docs/architecture/iri-identity-patterns.md:181-193` | no |
| PAT-41 | 5.4 Parent-relative key | **Name a part {parentIri}/part/{encodedImmutableKey} when its key is immutable within the parent.** | Moving the part to another parent creates a new IRI. | |  | `docs/architecture/iri-identity-patterns.md:181-193` | no |
| PAT-42 | 5.4 Parent-local ordinal | **Name a part {parentIri}/part/{ordinal} for an immutable authored sequence that is not reorderable.** | The ordinal must never be reused or renumbered. | |  | `docs/architecture/iri-identity-patterns.md:181-193` | no |
| PAT-43 | 5.4 Random child surrogate | **Name a part {parentIri}/part/{uuid4} when identity is needed but no stable key exists.** | A retry requires a claim or external correlation. | |  | `docs/architecture/iri-identity-patterns.md:181-193` | no |
| PAT-44 | 5.4 Blank node (retained blank-node pattern) | **Leave a node blank in a sealed graph with no external reference or multi-request update, which models RDF faithfully with no artificial identifier.** | No stable external identity, expensive canonicalisation for some graphs, and no direct update addressing. | |  | `docs/architecture/iri-identity-patterns.md:468-474` | no |
| PAT-45 | 6.3 Random surrogate pattern | **Mint an opaque UUIDv4 IRI when a node has no stable natural identity, disclosing no key and embedding no time.** | Independently repeated ingestion mints duplicates unless a separate correlation mechanism exists. | |  | `docs/architecture/iri-identity-patterns.md:284-294` | no |
| PAT-46 | 6.6 Content-addressed entity pattern | **Name an immutable resource by a digest of its content, deduplicating identical content and supporting verification and caching.** | It is unsuitable for mutable domain entities, since a changed state needs a new content identity. | |  | `docs/architecture/iri-identity-patterns.md:320-326` | no |
| PAT-47 | 8.1 Exact-RDF-term hashing | **Hash the RDFC-1.0 canonical N-Quads of the dataset without value normalisation, so the hashed graph is exactly the stored graph.** | Semantically equivalent lexical forms do not deduplicate, so producers must normalise before writing. | |  | `docs/architecture/iri-identity-patterns.md:424-432` | no |
