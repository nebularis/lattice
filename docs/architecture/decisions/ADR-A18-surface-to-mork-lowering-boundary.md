# ADR-A18: Surface-to-MORK lowering boundary

**Status:** Accepted
**Date:** 2026-09-18
**Supersedes:** none
**Related:** ADR-A17 (Surface unified projection authoring model), ADR-A16 (Surface projection mechanism), ADR-A19 (staged compiler architecture)
**Unit:** [`surface-mork-unified-projection`](../../developer/plans/surface-mork-unified-projection-plan.md) (epic)
**Source plan:** the Surface-MORK Unified Projection Program plan

## Context

MORK is the machine-facing, provenance-rich mapping graph. It already models `mork:DataMapping`, `mork:ShapeMapping`, `mork:RuleMapping`, `mork:QueryTemplate`, and `mork:ProjectionMapping`, with parameter bindings, targeting specs, and provenance records. The Surface outstanding items record (§3.7) confirms `mork:ProjectionMapping` already exists in `ontology/mork/spec/Mork.ttl` and that `tools/surface/mork.py` lowers in both directions against it.

Authoring MORK's mapping graph by hand — parameter bindings, targeting specs, dependency edges — is exactly the complexity ADR-A16's Surface layer was created to spare domain authors from for Promotion and Index. Projection needs the same relief.

## Decision

**A `srf:ProjectionContract` lowers deterministically into one or more MORK mapping nodes**, drawn from `mork:DataMapping`, `mork:ShapeMapping`, `mork:RuleMapping`, `mork:QueryTemplate`, and `mork:ProjectionMapping` as the contract's intent requires. MORK remains the canonical mapping graph: dependency edges, parameter bindings, and provenance live there, not duplicated in Surface. Surface never emits an executable artefact (SPARQL, SHACL, SWRL, RML) directly for a Projection contract — only a validated MORK graph, which downstream compilers (ADR-A19, ADR-A23) then target.

## Consequences

- A new lowering stage is required in the Surface compiler, distinct from Promotion/Index's direct-emit path.
- Lowered output must satisfy MORK's own completeness and validation checks before any backend compiles it — MORK validation is an acceptance gate for Surface's Projection output, not a downstream concern.
- The namespace and toolchain assumptions recorded as unverified in the Surface outstanding items record §5 (the `mork:` prefix binding, the exact term names `tools/surface/mork.py` assumes) must be confirmed against `ontology/mork/spec/Mork.ttl` as it stands, not re-guessed, before lowering is relied on in production.
- Promotion and Index keep their existing direct-emit path. This ADR does not require routing them through MORK.

## Addendum (2026-11-23): a derivation's expression is carried across, and a lowered derivation is a scheme with a source node root

**Status of this addendum:** Accepted by the maintainer on 2026-11-24.

The decision above lowers a projection into mapping nodes without saying what a derivation computes, so the operation of a derivation was written nowhere and a backend had to supply it. Surface now has a vocabulary to state it, and MORK has typed value expressions and an identity rule that writes on the source node.

1. **A derivation states its operation in the contract.** A derivation projection states an expression on its result-target role binding, over its evidence role bindings, in a closed vocabulary of typed expressions: sum, difference, product, quotient, a literal of a stated datatype, rounding to a stated scale, and a choice of two values on a comparison of two operands. The contract states and the compiler executes, so the operation is in the contract, where its laws are checked (`srf:P6` to `srf:P9`), and never in a backend's text.
2. **The lowering carries the expression across.** Each node of the expression becomes the MORK value expression of the same kind, with each evidence role binding it reads a typed reference to the property it binds. The lowering stays deterministic. Each node is named by its place in the contract's expression and each role by its place among the contract's role bindings, so the same contract gives the same graph in whatever order its triples were read.
3. **A lowered derivation is a mapping scheme.** Its root datum iterates the carrier class and takes the source node as its identity, so the assertion beneath it writes the result property on the carrier instance and no datum is minted or typed. The assertion's value is the lowered expression. The root also carries the targeting spec and a parameter binding for each role binding and each backend-policy field, as the bare mapping did. The lowered node is never typed `mork:ProjectionMapping`, which means lookup-class generation.
4. **The other kinds keep the bare mapping.** A graph construction, a join and an expansion lower as before until each has an expression of its own to carry. Surface still emits no executable artefact.
5. **A lowered scheme names its contract by a link.** The lowering writes `srf:producesMapping` from the contract to the root of its scheme, and from the contract to the bare mapping of the other kinds. The link is structure a reader follows, so a note carries no contract IRI, and the domain of the property is widened from a generated surface to a generated surface or a projection contract. A bare mapping keeps `mork:mappingFor`, which it already wrote. A backend reads the scheme with no knowledge of the contract, and a tool that needs the contract follows the link.

**Rejected.** The operation added to the lowered mapping by hand, which makes the lowering depend on a person and leaves the contract without its meaning. An approved template that names a query fragment, which holds query text where the contract states meaning. A datum minted for each carrier and linked to it, which changes what the contract states, a property of the carrier.

**Consequences.** A derivation that states no expression is refused, and so is one whose expression does not satisfy the laws, so a contract written before this addendum may need its operation added. MORK's shapes, with the new ones for value expressions and the source node identity, are the acceptance gate this decision's consequences name. A backend that reads a derivation's scheme can compile it with no knowledge of the Surface contract it came from.

## Addendum (2026-11-24): a graph construction states its node, and a lowered construction is a scheme

**Status of this addendum:** Accepted by the maintainer on 2026-11-24.

Item 4 of the addendum of 2026-11-23 leaves a graph construction as a bare mapping. A construction writes new structure, a node of a class, linked from the instance and carrying values read from it, and Surface's role kinds cannot say what that node is. This addendum replaces item 4 for this kind. A join and an expansion keep the bare mapping.

1. **A graph construction states its node in the contract.** The result-target role binding of a graph construction binds the link from each instance to the node and states `srf:constructedAs` a constructed node, so the result is a node where a derivation's is a value and a role keeps its one meaning. The constructed node states its class, its identity and each value it writes from an evidence role binding of the same contract (`srf:P10` to `srf:P13`). Its identity is a closed choice, a node for each instance or one node for each value of a key of required-evidence bindings, never implicit. A key is spelled into the identifier, so a key that may be personal or may change is no key, which Surface cannot check and the feature states as its boundary.
2. **A lowered construction is a mapping scheme.** The root iterates the carrier class and takes the source node as its identity, as a derivation's does. Beneath it a contextual datum mints and types the constructed node, is glued to the instance by the link, and is guarded by every required-evidence binding, so an instance that lacks one contributes nothing at all and is reported, even where another instance has made the node. An assertion beneath the datum writes each value from its evidence binding. The identifier of a node for each instance is a hash of the instance's identifier, and a keyed node's is read from the key's values in the order of their properties. Both carry the contract's key and the class, so two contracts never reach one node.
3. **The lowering stays deterministic.** Each node, guard, identity part and assertion is named by its place in the contract, the written values in the order of their properties, so the same contract gives the same graph in whatever order its triples were read. The lowering writes `srf:producesMapping` as for a derivation.
4. **The class decides the signature scope.** A node typed with a class minted in the contract's target namespace is local-signature. One typed with a class an authored vocabulary declares reaches the authored signature, and `srf:P1` reads it as source-signature.

**Rejected.** A second result-target binding for each written property, which relaxes `srf:P3` and gives roles a second meaning. A new role kind for the node, which does the same for roles by kind. The hash of the instance's identifier as the only identity, which leaves a merge impossible to state.

**Consequences.** A graph construction that states no node is refused, and so is one that does not satisfy the laws, so a contract written before this addendum may need its node added. A keyed construction merges instances, so it takes the mapping review of ADR-A41's addendum and the compiler reports it. MORK's shapes are the acceptance gate for the scheme. No MORK term is added.

## Addendum (2026-11-24): a join states its relation, and a lowered join is a scheme

**Status of this addendum:** Accepted by the maintainer on 2026-11-24.

Item 4 of the addendum of 2026-11-23 leaves a join as a bare mapping. A join relates an instance to an instance of a second class that is already in the graph, by a value both hold, and Surface's role kinds cannot say what relates them or how many the value may name. This addendum replaces item 4 for this kind. Only an expansion keeps the bare mapping.

1. **A join states its relation in the contract.** The result-target role binding of a join binds the link from each instance to the instance it names and states `srf:joinedAs` a join statement, so the result is a link where a derivation's is a value and a construction's a node, and a role keeps its one meaning. The statement pairs evidence role bindings, each pair a binding that reads a value of the contract's own carrier and one that reads a value of a second carrier, which `srf:bindsCarrier` names, and the relation is equality of the two values. A composite key is several pairs, all of which must hold. The statement states how many instances of the second carrier one value may name, `srf:AtMostOne` or `srf:AnyNumber`, counted for each value, so an instance with two codes that each name one customer has two links. A contract may omit it, and then it is at most one, stated in the term's definition. A second rule, `srf:joinLinks`, says how many links one instance may have, `srf:AtMostOne` or `srf:AnyNumber`, and is any number where omitted. The lowering writes both into MORK, so the compiled form leaves neither implicit (`srf:P14` to `srf:P17`). A join writes the link and copies nothing, so a value of the second instance is reached through the link by a read path.
2. **A lowered join is a mapping scheme.** The root iterates the carrier class and takes the source node as its identity, as a derivation's does. Beneath it a datum iterates the second carrier's class, takes the node it finds as its own identity, states each equality as a `mork:JoinCondition` with its own comparison, states how many nodes a value may find, how many links an instance may have and how an instance with no match is reported, and is glued to the instance by the link. It is guarded by every required-evidence binding of the contract's own carrier, tested on the instance, so an instance that lacks one contributes nothing and is reported. The guard holds the instance's required evidence and never the matched node's beyond the key it was matched on, so a required value of the second carrier other than the key is not checked by the join. Nothing is built for it.
3. **The evidence kind says what a missing match means.** A join is on required evidence or on candidate evidence, and every binding of its statement is of one kind. On required evidence an instance that holds the values and finds no instance of the second carrier writes no link and is reported as a warning. On candidate evidence it writes nothing and is reported as information, and an instance that lacks the values says nothing. Under at most one a value that finds several writes no link for that value and is reported with each, under any number it writes a link for each. Under at most one link an instance whose values together find several writes no link and is reported with each.
4. **The lowering stays deterministic.** The datum, the guard and each condition are named by their place in the contract, the conditions in the order of the properties they compare, so the same contract gives the same graph in whatever order its triples were read. The lowering writes `srf:producesMapping` as for a derivation. Each pair states its own comparison. The datatype the second carrier's binding states is the pair's, the instance's value is cast to it and joined as the same term, and a pair whose binding states none is compared as the same term, so one key may compare a string pair and an integer pair and a pair may cast one side. The lowering states each comparison on the condition and none on the datum, since a condition that states none is a term comparison and nothing is inherited. A left binding that states a datatype has a right one to cast it to.
5. **The link decides the signature scope.** A link minted in the contract's target namespace is local-signature. One an authored vocabulary declares reaches the authored signature, and `srf:P1` reads it as source-signature.

**Rejected.** The existing terms alone, with the pairing taken from the order of the evidence bindings, which leaves the meaning implicit. A path already in the graph that reaches the second instance, which is a read path and so a promotion. A value copied from the second instance onto the first, which goes stale where the second changes. A lookup over reference data, which cannot read the second class from the source.

**Consequences.** A join that states no relation is refused, and so is one that does not satisfy the laws, so a contract written before this addendum may need its statement added. A join takes ADR-A41's mapping review, which the compiler records as a finding on every join. MORK gains the terms ADR-A23's addendum names, and its shapes are the acceptance gate for the scheme.

## Addendum (2026-11-25): an expansion states its members, and a lowered expansion is a scheme

**Status of this addendum:** Accepted by the maintainer on 2026-11-25.

The addendum of 2026-11-24 for joins leaves an expansion as a bare mapping, the one kind that stated nothing the lowering could carry. An expansion restates one relation of an instance as a statement for each member, which Surface's role kinds cannot say. This addendum replaces the sentence that leaves it bare, so every projection kind now lowers into a scheme.

1. **An expansion states its members in the contract.** The result-target role binding of an expansion binds the property each member is written as and states `srf:expandedAs` an expansion statement, so the result is a statement on the instance for each member, where a derivation's is a value, a construction's a node and a join's a link, and a role keeps its one meaning. The statement names one evidence role binding of the contract's own carrier with `srf:expandsFrom` and states its members as exactly one of a named source and a SHACL property path from the instance, `srf:membersPath`. A path takes the forms `sh:path` takes, a property, a sequence, an alternative, an inverse, zero or more and one or more, and reads the property of the binding it expands from and never the property the result-target binding writes, so an expansion cannot feed on its own output. The two named sources are a list's members, `srf:ListMembers`, and a property's transitive closure, `srf:TransitiveClosure`, which the lowering writes as the paths `<property>/rdf:rest*/rdf:first` and `<property>+`.
2. **A lowered expansion is a mapping scheme.** The root iterates the carrier class and takes the source node as its identity, as a derivation's does. Beneath it one assertion writes the property the result-target binding binds on the instance, with the path as its reference, so each member is a statement on the instance and nothing is minted or typed. A node for each member is not stated by this kind. The assertion is guarded by every required-evidence binding of the contract's own carrier, so an instance that lacks one contributes nothing. An expansion on candidate evidence has no guard.
3. **An empty or missing source writes nothing.** On required evidence an instance without the property is excluded and reported. An instance that holds the property and whose path reaches no member is reported as information. On candidate evidence an instance that lacks the property says nothing, as a join does, and only one that holds it and reaches no member is reported. The contract states no bound on the number of statements, since that number depends on the data.
4. **The lowering stays deterministic.** The root, the assertion and the guard are named by their place in the contract, so the same contract gives the same graph in whatever order its triples were read, and a path a contract states and the named source it equals lower to the same scheme. The lowering writes `srf:producesMapping` as for a derivation.
5. **The property decides the signature scope.** A property minted in the contract's target namespace is local-signature. One an authored vocabulary declares reaches the authored signature, and `srf:P1` reads it as source-signature.

**Rejected.** The members as a fan-out of one value under several properties, which is bounded by the contract and which reasoning over `rdfs:subPropertyOf` already does. A delimited string split by a separator, which needs a string operation SPARQL lacks. A subgraph obtained by SHACL evaluation, which selects instances by conformance and is not what an expansion is. A bound on the number of members, whose order and refusal are modelling choices of their own. A node for each member, which combines an expansion with a graph construction.

**Consequences.** An expansion that states no members is refused, and so is one whose members read the property it writes and one that does not satisfy the laws, so a contract written before this addendum may need its statement added. An expansion takes ADR-A41's engineering review, which the compiler records as the finding `ExpansionReview` on every expansion. MORK gains no term, and its shapes are the acceptance gate for the scheme.

## Addendum (2026-11-25): a node for each member, and a lowered expansion that constructs is a scheme

**Status of this addendum:** Accepted by the maintainer on 2026-11-25.

The addendum of the same date for expansions leaves a node for each member out, since a contract has one projection kind and the two statements it would combine were each stated by a kind of their own. This addendum states them together on one binding, so an expansion can construct a node for each member it reaches.

1. **Both are stated on the result-target role binding, and the contract is an expansion.** The binding binds the link from the instance to each node and states `srf:expandedAs` the members and `srf:constructedAs` the node made for each. Each term keeps its meaning. A graph construction states no expansion, and an expansion states a construction only beside its expansion statement on that one binding, so `srf:P10` and `srf:P18` say that the two are stated together only there, and `srf:P22` states it.
2. **The identity states what a node is for.** `srf:PerInstance` is one node for each instance and member. `srf:ByKey` is one node for each value of the key, whose parts are the instance's required-evidence bindings and, where `srf:keyMember` states it, the member, at least one part in all and the member at most one (`srf:P24`). A list that repeats a member gives one node for it. A new individual, `srf:MemberNode`, makes the member itself the node, which types the member, links it and writes on it and mints nothing, and applies only where the members are nodes. The member terms are stated only beside an expansion statement (`srf:P23`).
3. **A node writes the member or a value of the instance.** A written value states exactly one of `srf:fromBinding` and `srf:fromMember` (`srf:P25`). A blank member that has a stable name is written as the name's value and never copied as a blank node. A value of the member's own properties is never copied by the construction, which would leave it stale. A join from the constructed node to the member, or to the record that holds the property, models it where it is wanted.
4. **A stable name is selectable.** `srf:memberName` names a property of the members whose value is known to be unique for them, and the identity spells that value in place of the member, so a member that is a blank node can have a name. A member without the value, or a blank node where none is named, is reported and skipped at run time, while the instance's other members are written.
5. **A lowered node for each member is a scheme.** It is the scheme of a graph construction, with its contextual datum stating the expansion's path as `mork:memberRef`, which binds the member once for the datum's identity, its link and each value. A keyed node's template ends in a `mork:MemberExpression` where the key states the member, a node for each instance and member states no template and takes MORK's default, a stable name is `mork:memberName`, the member as the node is `mork:identityRule mork:MemberIdentity` with no template or name, and a value written from the member is an assertion that states `mork:dataMember`. The guard is every required-evidence binding of the contract's own carrier, as for a construction, and the lowering stays deterministic.
6. **Two reviews, by the kind each part is.** A node made for each member takes the expansion review ADR-A41 asks, recorded as `ExpansionReview`, and a keyed node, or the member as the node, takes the mapping review, recorded as `MappingReview`.

**Rejected.** A third projection kind of its own, which breaks the count of four kinds. A constructed node that names an expansion it is made from, which states the pairing in a second place. A key that reads a position in the list, which SPARQL's list path does not number. A copy of the member's properties onto the node, which goes stale where the member changes.

**Consequences.** A construction that states an expansion, a member term outside an expansion and a written value that names both or neither source are refused. A contract that keys a node on a member it cannot name in a stable way takes a run-time report for each blank member, and a key is spelled into an identifier as before. The new Surface terms and laws, and the MORK terms `mork:memberRef`, `mork:memberName`, `mork:dataMember`, `mork:MemberExpression` and `mork:MemberIdentity`, are released in minor versions of their modules at the merge, by `mise run version:bump`.
