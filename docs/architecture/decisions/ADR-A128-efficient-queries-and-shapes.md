# ADR-A128: Efficient queries and shapes

## Context

The ontology test suite (`check:ontology-catalog`) took 427 s on a four-core machine, and 237 s on a laptop, and for that reason
no continuous integration ran it. Finding the causes took several weeks of profiling work in one session, and the causes were
of different kinds.

- Some are properties of **rdflib**, the SPARQL engine the shapes are validated on in our tests. It parses and translates a
  query's text on every call, fixes the order of a group's patterns before it knows which variables are bound, applies a
  `FILTER` after the whole group, and joins a chain of three groups by building the later ones whole.
- One is a property of **pySHACL**, which runs a SHACL-SPARQL constraint once per focus node and writes the `PREFIX` block in a
  varying order.
- Some are properties of **our harness** (a fixture parsed once per test, scheduling by file) or of **the machine** (power
  mode, memory pressure, more workers than cores that do real work).
- Oxigraph, run on the same query forms through the adapter of ADR-A125, showed none of the sensitivity that rdflib showed.

A rule learned on one of these is wrong on another. A shape rewritten to suit rdflib's planner does not make Oxigraph faster, and
a shape written for a better planner can be many times slower on rdflib. Without a record, each author relearns this, and a
rewrite made for speed can change what a shape accepts.

## Decision

1. **The record.** [efficient-queries-and-shapes.md](../efficient-queries-and-shapes.md) is the project's design record for
   writing queries and shapes that run in reasonable time and for keeping the test suites that run them fast. Authors of
   SHACL-SPARQL constraints, of SPARQL generated by a compiler, and of test harness code that runs either follow its rules
   (R1 to R8 for queries and shapes, H1 to H8 for the harness) or record why they do not.
2. **Every performance claim carries its scope.** A statement about speed names what it holds for: the specification, rdflib,
   pySHACL, Oxigraph, our harness, the JVM or the machine. The record's scope tags and its table of what is specific to
   rdflib are the convention. A rule is stated as a hypothesis for any engine we have not measured.
3. **A shape stays correct on every engine.** A rewrite for speed uses SPARQL 1.1 and SHACL-SPARQL as specified, and no form that
   only one engine accepts. It does not use SHACL-AF SPARQL targets, which are a portability risk. Speed on rdflib is an
   optimisation of a portable query, never a reason to write a non-portable one.
4. **A rewrite for speed is a replayed change.** Before one is committed, every validation the suite performs is recorded
   against the old shapes and replayed against the new ones, and the results are compared, with the cases that did not
   reproduce on the old shapes alone subtracted (R7). A rewrite that is equivalent on that evidence is a PATCH change to the
   shapes' version (ADR-A86), and a negative test exists for every constraint it touches.
5. **The evidence lives in two places.** What each store and validator does, and how we found out, is recorded in
   [triple-store-discovery.md](../triple-store-discovery.md) (TSD-22 to TSD-33 for this decision). A measurement that anyone
   can repeat is a benchmark under `benchmark/` (ADR-A124), here `benchmark/sparql-constraint-query-cost`, run as
   `mise run check:sparql-constraint-query-cost`. It runs the same query forms on rdflib and Oxigraph, and fails on a wrong
   result, never on time.
6. **Agent guidance points at the record.** `AGENTS.md` and the skills for ontology authoring, testing, design and triple
   stores direct an agent to the record before it writes or changes a constraint query, a generated query or a fixture, so
   that the rules are applied to new work (ADR-A117).
7. **The record is revisited when an engine or validator changes.** Its section 7 lists, for each rule, what to re-measure.
   An upgrade of rdflib, pySHACL or the reference engine is a reason to run the benchmark and re-read the table.

## Consequences

- The default `check:ontology-catalog` run is fast enough to run in continuous integration. That is a separate decision of the
  maintainer.
- Some rules are rdflib workarounds. Where rdflib fixes a cause, the corresponding rule loses its reason, and the record says so
  in its table. The rewrites already made stay correct on every engine and are not reverted.
- A reader who wants a quick answer reads the table in section 2 of the record. A reader who wants to change a query reads
  section 4.1, its checklist.
- A rewritten shape needs a version bump, its README and the generated release notes updated, and a tag, which is the
  maintainer's.
- What we have not measured is listed (section 8 of the record and TSD-Q14 to TSD-Q18). Those items are hypotheses, and an
  author who depends on one measures it first.
