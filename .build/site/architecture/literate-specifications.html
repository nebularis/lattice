Literate specifications

Status: Accepted with ADR-A126, 2026-10-17. The extractor implements them, and Eligibility is the first module migrated to them. Until a module’s README is migrated, the current conventions at the end of this document apply to it.

A LATTICE module’s README.md is its specification. The normative sections are read by tools/literate_extract.py, which writes the module’s Turtle and SHACL from them, so each fact about a term is written once. This document describes the layout every README takes, the grammar of its Description Logic Encoding section, the markers it may carry, and how text becomes Turtle. A README’s section 3 links here and states only what is specific to its module.

The layout

§ Section Required Normative Extracted to
1 Purpose and Scope yes yes the ontology’s dct:description
2 Namespace and Prefixes yes yes prefixes, the ontology header, creators and contributors
3 Extraction Contract yes yes the module’s repository catalogue entry
4 Overview yes no nothing - holds the generated class diagram, narrative explanation of the layer, and other diagrams if needed
5 Detailed Design yes no nothing - purely informational
6 Description Logic Encoding yes yes the spec and vocab documents
7 Shapes yes yes the shape files
8 Examples yes no nothing - example files are written by hand and linked from here
9 Canonicalisation no yes nothing
10 Formalisation no yes isabelle-spec blocks, to the module’s Isabelle theory and the Python generated from it
11 Dependencies yes no nothing
12 Release Notes yes yes nothing. Checked
13 Open Issues yes no nothing
  • Numbers are fixed. An absent optional section keeps its heading and says “Not applicable.” An empty subsection keeps its heading and says “None.”
  • No section of a module’s own. Material that fits no section goes into a subsection of Detailed Design or of Open Issues.
  • Sections are found by title. The extractor warns when a section’s number differs from this layout.
  • Normative sections win. Where a non-normative section disagrees with a normative one, the normative section is the specification. Overview and Detailed Design explain the model and never add to it.
  • Sources. A README cites only published decisions and never a working document such as a sketch, plan or status record (ADR-A127).

Sections 1 to 3

Section 1 becomes the dct:description of every document the README generates, rendered as plain text (see “From markdown to Turtle”). Text that should stay in the README only is wrapped in an exclude region. A table, a heading or an image in section 1 is refused unless it is excluded.

Section 2 holds up to three tables, recognised by their columns. The header table is required, and the other two are optional. The values below are illustrative.

  • The header table has one row for each document the README generates, a .ttl path under spec/ or vocab/. Each document opens with its own ontology header: the ontology IRI, the version IRI, and an owl:imports for each IRI in the Imports cell, separated by commas or spaces. The version IRI is written in full, since not every ontology’s version IRI extends its ontology IRI. It ends in the version (X.Y.Z), and a module’s spec documents share one version, as its vocab documents do. Every fenced block the README extracts must go to a document this table names.
  • The prefix table gives each document’s @prefix lines. rdf:, rdfs:, owl:, xsd: and dct: are added with their standard namespaces where the table omits them, and binding one of them to another namespace is refused.
  • The creators and contributors table. Each person is identified by an IRI, an ORCID iD where the person has one and their GitHub profile otherwise, and becomes a dct:creator or dct:contributor of every document. The display name is filled only with that person’s express permission, and is never written to a generated file. The maintainers keep the table.

Every generated document declares the Dublin Core terms it uses as annotation properties itself, with the dct: prefix, and never imports Dublin Core, so it stays in OWL 2 DL. A document’s ontology header comes first, then its other statements sorted by subject, then the README’s blocks for it, ordered by their own text, so moving a block in the README changes no generated file. A block of a README in the layout declares no prefix of its own, since the prefix table is the one source of prefixes.

Section 3 holds the module’s catalogue entry, exactly one fenced toml repository-catalogue block, which the layout check requires inside section 3. It names the module’s spec documents, vocab documents, shape files in order and permitted imports. Its spec and vocab documents are the rows of section 2’s header table, written twice, and a check holds the two lists equal. Its prose says only what is unusual about the module, for example a second spec document, and links here for the rest.

Section 6, the Description Logic Encoding

Section 6 is the only source of the module’s axioms. Its subsections are 6.1 Classes, 6.2 Object Properties, 6.3 Datatype Properties, 6.4 Individuals, 6.5 Disjointness and Keys, 6.6 Other Axioms and 6.7 Axiom Index, each headed ### 6.N Title. All seven are present, an empty one saying “None.”, and no other is allowed. A subsection may open with prose before its first entry or table, which is not extracted.

Entries and the rows of 6.5 go to the module’s main spec document, spec/<name>.ttl, and individuals to its main vocab document, vocab/<name>-vocab.ttl. An output-file region sends what it encloses to another document. Either way the document must be a row of section 2’s header table.

Entries

An entry is a level-4 heading holding one CURIE in backticks, followed by labelled paragraphs and tables. A labelled paragraph starts a line with a bold label ending in a full stop, and runs to the next blank line. Every paragraph of an entry starts with a label, an unknown label is an error, and a label that does not apply to the entry’s kind is an error. A term has one entry.

Label Applies to Produces
**Definition.** every term, required rdfs:comment
**Utility.** every term fnd:utility
**Label.** every term rdfs:label, which is never derived from the local name
**Preferred label.** every term skos:prefLabel
**Subclass of.** class one rdfs:subClassOf per comma-separated class expression
**Equivalent to.** class owl:equivalentClass, one class expression
**Key.** class owl:hasKey
**Restrictions.** class the restriction table, below
**Domain.**, **Range.** property rdfs:domain, rdfs:range, each a class expression or a datatype
**Characteristics.** property functional, inverse functional, transitive or symmetric
**Inverse of.**, **Subproperty of.** property owl:inverseOf, rdfs:subPropertyOf
**Scope note.** any term skos:scopeNote. Further annotation labels are added the same way

An annotation’s text becomes plain text, as section 1 does. Written as a Turtle literal instead, for example "Wording node"@en, it is used as written, which is how a language tag or a datatype is given. A comma-separated label (Subclass of, Key, Characteristics, Subproperty of) splits only at commas outside parentheses. skos: and fnd: must be in the prefix table for a label that uses them.

Class expressions

Class expressions are written in OWL Manchester syntax with CURIEs: and, or, not, some, only, value, min, max and exactly, with parentheses for nesting. and binds tighter than or, and not tighter than both. min, max and exactly take a whole number and an optional class, which makes them qualified. Literals use Turtle’s forms, for example value "x"^^xsd:string, value "x"@en or value 5. An enumeration is written in braces, for example { elg:Forward, elg:Inverse }, and is an enumerated class (owl:oneOf) of individuals, or an enumerated data range of literals. A union, intersection or complement is written with a owl:Class, as the layers already write them. For example, (ins:Obligation or ins:Permission) is a union, and spc:hasGuardExpression some (spc:Expression and spc:hasExpressionSort value spc:bool_sort) nests an intersection inside a restriction.

Restrictions

The restriction table has four columns. Values holds the body of a Manchester restriction. Asserted in says where the restriction holds: blank for OWL and SHACL, OWL for OWL only, SHACL for SHACL only. Message is an optional sh:message.

An OWL restriction also holds in SHACL by default, since some restrictions guide the reasoner at design time and are checked on data as well. A qualified restriction is never mapped to sh:class with counts. The OWL form allows other values that are not C, and sh:class forbids them. only maps to sh:datatype when its filler is an xsd: datatype, rdfs:Literal or rdf:langString, and to sh:class otherwise.

Generated SHACL goes into the module’s shapes/structural.ttl, which is generated whole: one <Class>Shape per class with a row checked in SHACL, targeting that class, and one property shape per property and message. Rows for one property with the same message, or none, share a property shape, so max 1 and only xsd:boolean become one, as the layers write them today. Two such rows that state the same constraint are refused. The shapes carry no sh:severity, so each is a violation. A shape the table cannot state, such as a SPARQL constraint or a warning, is written by hand in section 7, in a block that names its file, which may not be shapes/structural.ttl. In a README in the layout every shape block names its file.

Individuals, disjointness and other axioms

Section 6.4 lists individuals in tables whose first two columns are Individual and Type, followed by any of the annotation columns Label, Preferred label, Definition, Utility and Scope note. Type holds one or more names, separated by commas, so an individual that is also an owl:NamedIndividual says so. Section 6.5 holds **All disjoint.** paragraphs, each naming two classes or more, which become one owl:AllDisjointClasses with its members in the order written, and **Disjoint.** paragraphs, each naming exactly two, which become an owl:disjointWith. Section 6.6 holds turtle-spec and turtle-vocab blocks, visible or hidden, for what the grammar does not express, for example property chains, or an individual with a statement the table’s columns cannot hold, which is written whole. Such blocks declare no prefixes, since section 2’s prefix table is their one source, and their order in the README does not matter.

Generated views

The Axiom Index and the Overview’s class diagram are generated from section 6 and written into the README by the extractor, each in its own region: <!-- start: {"generated": "axiom-index"} --> inside 6.7 and <!-- start: {"generated": "class-diagram"} --> inside section 4, each closed by <!-- end -->. Both regions are required, once each, in those places. The extractor rewrites what is between the markers, and --check reports the README as drift when a region is out of date, for example after a hand edit. Neither region is read as part of section 6.

The Axiom Index is a table of every term, classes first, then object properties, datatype properties and individuals, each sorted by name. Its summary column states a class’s superclasses, equivalent class, key, disjoint classes and restrictions (marked “OWL only” or “SHACL only” where a row says so), a property’s domain, range, characteristics, inverse and super-property, and an individual’s types.

The class diagram is a mermaid classDiagram. It shows:

  • each class, with its restrictions as members in words, for example “matchStrategy, exactly one” or “items, at least two Item”
  • a datatype property with a domain as a member of that class, with its range, for example “code (xsd:string)”
  • subclassing as <|--
  • an object property with a named domain and range as an association arrow labelled with its name
  • a property with no named domain as a box of its own, for example “Object Property - relatesTo”

Classes are named by their local names, qualified by their prefix where two would share one. The diagram draws no composition arrows, since nothing in section 6 says which associations are aggregates.

Markers

HTML comments carry four kinds of marker. A region opens with <!-- start: {...} --> and closes with <!-- end -->, which closes the innermost open region. The keys are exclude (a boolean), output-file (a path inside the module) and generated (the name of a generated region). Any other key is an error. A marker written inside a fenced block is text.

Excluding text from an extracted region, for example a diagram in section 1.

output-file has a second form, the # @output-file "spec/<file>.ttl" first line of a fenced block (ADR-A120). Both forms apply to every extracted block kind, and a block may carry only one. A hidden block may not contain -->, which would end the comment early. Mermaid diagrams are never hidden.

From markdown to Turtle

  • Plain text. Backticks and emphasis are removed. List items stay as lines beginning - . A table inside an extracted region is an error.
  • Links become their text followed by an absolute URL at the release tag that the section 2 version names, so a released document never points at a moving target.
  • Order. Generated Turtle is sorted by subject, then by a fixed order of predicates, so reorganising a README changes no generated file.
  • Versions. Generated documents are tracked and versioned as the versioning policy describes. A module’s first regeneration under this layout is one PATCH release, and its graph is the same as before except for reconciliations the maintainer approves. mise run check:literate-migration -- <module> <ref> --reconciliations <file> compares every file the module generates with the file at a git ref, and passes only when each difference is listed.

Release Notes

Every version named in section 2, and every released version in the release register, has an entry. An entry says what changed and which documents moved, and cites only published decisions.
