Efficient queries and shapes

What this is. The project’s record of how to write SPARQL queries and SHACL shapes that run in a reasonable time, and how to keep the test suites that run them fast. It says what we measured, why it happens, what we decided to do about it, and, for every statement, whether it holds for any SPARQL engine or only for the engine, validator or machine we measured it on.

Status: a living record, begun 2026-10-17 from the work that took the ontology test suite (check:ontology-catalog) from 427 s to about 70 s on a four-core machine and from 237 s to 36 s on the maintainer’s laptop. The rules are decided in ADR-A128. The evidence for each mechanism is in triple-store-discovery.md, findings TSD-22 to TSD-33, and is reproduced by a benchmark, mise run check:sparql-constraint-query-cost.

Versions covered: rdflib 7.6.0, pySHACL 0.40.1, pyoxigraph 0.5.11 (Oxigraph), pytest-xdist 3.8.0, Temurin 25.0.4, Python 3.14. A statement holds for these until it is checked again.

1. How to read this document

1.1 Scope tags

Every rule and finding carries one of these, because the same observation can be a fact about SPARQL, about one engine, or about our own test code.

1.2 Evidence

The words are those of the discovery record: Source (we read the code at a named version), Observed (we ran a probe and a script or a test shows it), Documented (the tool’s own documentation says so) and Reasoned (it follows from other statements and is not yet observed, so it is a hypothesis). A statement without a tag of evidence is Observed.

1.3 Where the numbers come from

Run records follow the discovery record’s convention, the kind of machine and never the machine or person. R-D is a Linux x86_64 container with four logical cores and 15 GB. R-E is a macOS arm64 laptop with four performance and four efficiency cores and 8 GB. Both ran Python 3.14 with the versions above. Timings on a shared container drift by 10 to 15% between runs, so a ratio between two runs of the same session means more than an absolute figure. The measurements are collected in §9.

2.2 In words

  • Facts about SPARQL and SHACL. The two forms in each of R1 to R4 mean the same on every engine. That is what makes the rewrites safe to apply anywhere, and safe to check by comparing results. A FILTER applying to its whole group, EXISTS being evaluated with the current solution substituted, and a SHACL constraint being defined per focus node are all in the specifications.
  • Facts about rdflib. How fast the forms are is not in any specification. rdflib fixes the order of the patterns of a group when it translates the query, before it knows the initial bindings, and does not move a filter ahead of the patterns it guards (TSD-25, TSD-27). It evaluates a chain of three or more groups by building the later ones whole (TSD-26). It parses a query’s text with a pure-Python grammar on every call (TSD-22). Oxigraph, which plans queries itself, showed none of the first three (E1 to E3: its naive forms ran in 0.04 to 0.15 ms, within 1.5 times of the improved forms).
  • Facts about pySHACL. It runs a constraint once per focus node (TSD-23), writes the PREFIX block in a varying order (TSD-24) and copies the data graph for every validation (TSD-31). Another validator may do none of this. This is why a shape that targets a common class is expensive here (R5).
  • Defects. rdflib drops a constant false FILTER (TSD-32) and Oxigraph returns no row for COUNT(*) over one it can fold (TSD-33). These are not performance matters. They are reasons to write queries a particular way.
  • Facts about our harness and machines. H3 to H7 do not depend on the engine at all.

2.3 The consequence

The rules for writing a query (R1 to R4) buy their benefit on rdflib. We apply them because rdflib is the engine that runs our shapes in the test suite and in any continuous integration, and because they cost nothing in meaning. If shapes were validated by another engine, those rules would become optional and the measurements in §9 would need repeating there (§7). We have not shown that any other engine is insensitive, only that Oxigraph was on the experiments we ran.

3. Where a validation spends its time

A SHACL-SPARQL validation on rdflib is several layers, and a cost can sit in any of them.

flowchart TB
  T["a test"] --> C["harness: build the data graph<br/>parse, merge, copy, fingerprint"]
  C --> V["pySHACL validate()<br/>copies the data graph (TSD-31)"]
  V --> F["for each shape, for each focus node (TSD-23)"]
  F --> Q["Graph.query(text, initBindings)"]
  Q --> P["parse and translate the text (TSD-22)"]
  P --> E["evaluate: pattern order, joins, filters (TSD-25 to TSD-27)"]
  E --> R["result rows, report"]
  T --> J["reasoner call: JVM start, load, reason"]

3.1 The cost of a node shape

The cost of a node shape on pySHACL and rdflib is the number of its focus nodes times the cost of one run, plus a fixed cost per validation.

cost of a shape  =  focus nodes  x  ( per-run overhead + parse (if not cached) + evaluation )
cost of a test   =  building its data  +  validations  x  ( copy of the data + the sum of its shapes' costs )  +  reasoner calls

The per-run overhead is pySHACL’s own checks of the text, about 0.4 ms. Parsing is 20 ms for a twenty-line query when it is repeated. Evaluation is what §4 is about and ranged from 0.04 ms to 266 ms in the queries we measured.

3.2 Where six of the largest test files spent their time

Six files (test_wording, test_exposure_ontology, test_constitutive_terms, test_instrument, test_parameter_bindings, test_regimes) accounted for 75% of the suite’s test time. We instrumented them with the translation cache already in place, running the six at once on four cores (R-D), so the absolute figures are inflated and the shares are what matter.

4. Rules for queries and shapes

Each rule says what to do, why, what it cost and gained where we measured it, and which scope (§1.1) the benefit has. The examples are generic. The measured cases are in §9.3. A rule is a default and not a law, so measure when it matters (§6).

R1. Check a fact about a bound variable with FILTER EXISTS or FILTER NOT EXISTS

Do. When a pattern exists only to test something about a variable that an earlier pattern binds, write it as FILTER EXISTS { … }, or NOT EXISTS, and not as a pattern of the group. When a test asks for another node with the same value, look the other node up by the value inside FILTER EXISTS.

# a pattern that types ?s, which $this ex:inScheme ?s binds
$this ex:inScheme ?s . ?s a ex:Scheme .
# the same test, once ?s is bound
$this ex:inScheme ?s . FILTER EXISTS { ?s a ex:Scheme }

# "another node of the scheme has the same code": a join of every node
$this ex:inScheme ex:S ; ex:code ?c . ?o ex:inScheme ex:S ; ex:code ?c . FILTER (?o != $this)
# a lookup by the code
$this ex:inScheme ex:S ; ex:code ?c . FILTER EXISTS { ?o ex:code ?c . FILTER (?o != $this) FILTER EXISTS { ?o ex:inScheme ex:S } }

Why. rdflib orders the patterns of a group when it translates the query, by how many of their variables are not yet bound by the patterns before them, and $this counts as unbound then because initial bindings arrive only at run time. The pattern ?s a ex:Scheme has one unbound term and sorts ahead of $this ex:inScheme ?s, which has two. So rdflib scans every node of the type for each focus node, and the cost grows with the data (TSD-25). EXISTS is evaluated per solution with that solution’s values substituted, so inside it the variable is already bound and the pattern is a lookup.

Gain, rdflib. The scheme test cost 0.7 ms of 1.4 ms per concept in a real rule, and the EXISTS form cost 0.19 ms in all. A uniqueness test grew from 3.5 ms to 13.8 ms per focus node as the data grew from 200 to 800 nodes while the lookup form stayed at 0.2 ms, and the peril rules went from 2.0 s to 0.11 s over 405 focus nodes. Oxigraph: no difference.

Scope. rdflib. Not when: the pattern also binds a variable the query returns or uses later, since EXISTS binds nothing for the rest of the group.

R2. Keep a group to two operands, or move a dependent operand into EXISTS

Do. In a group of a basic pattern followed by braced groups, UNIONs or OPTIONALs, do not add a third part that depends on a variable the first two bind. Put it inside FILTER EXISTS, or in the group of the part that binds the variable.

Why. rdflib joins a group lazily, passing the left side’s bindings into the right side, only when no operand is itself a join. A chain of three or more parts is left-deep, so its outer joins evaluate their right operand whole and hash-join. For a constraint query the left side is one row, because $this is pre-bound, so an operand such as ?parent skos:notation ?parentCode is built over every notation for each focus node (TSD-26). Evaluating whole is cheaper when the left side is large, so this is a rule about constraint queries and not about joins in general.

Gain, rdflib. The peril parent-code query went from 2.3 s to 0.13 s over 405 focus nodes by this rule and R1 together. Scope. rdflib. W8 (wording) halved when its identity lookup moved ahead of its pair enumeration, and we do not know why (TSD-Q15), so treat that gain as an observation and not as support for this rule.

R3. Put cheap guards in a group of their own, ahead of an enumeration

Do. If a query has filters that read only $this and a variable bound early, and it then enumerates many candidates, put the early patterns and the guards in a braced group at the start.

# the guard filters apply to the whole group, after every candidate is built
SELECT … WHERE { $this ex:variable ?g . $this ex:value ?a . $this ex:value ?b . FILTER (?a < ?b)
                 FILTER EXISTS { $this ex:kind ex:Interval } }
# the guard runs first, and a node it rejects never reaches the enumeration
SELECT … WHERE { { $this ex:variable ?g . FILTER EXISTS { $this ex:kind ex:Interval } }
                 $this ex:value ?a . $this ex:value ?b . FILTER (?a < ?b) }

Why. A FILTER applies to its whole group (spec, §4.3 of the discovery record), and rdflib builds every solution of the group before it tests any (TSD-27). The two forms mean the same exactly when the guards read only variables the sub-group binds.

Gain. rdflib, 14 to 27 times when the guards reject 90% of nodes, and 2 times on the real wording slots. Oxigraph, 1.3 to 1.5 times. Scope. rdflib mostly. Not when: the sub-group binds a variable with many values, which multiplies the rows (our first reproduction did, and came out 0.6 times).

R4. Test absence with FILTER NOT EXISTS, and pure existence with FILTER EXISTS

Do. Prefer FILTER NOT EXISTS { … } to OPTIONAL { … } FILTER (!BOUND(…)) and to GROUP BY … HAVING (COUNT(…) < 1). When a pattern exists only to prove that something exists, and its variable is used nowhere else, write FILTER EXISTS, which does not multiply the rows.

Gain. Small. 1.4 times against the count form on one rule, 1.0 to 1.2 times against OPTIONAL plus !BOUND on both engines (TSD-28). Scope. little anywhere. Take it when rewriting for another reason. Do not release a shapes version for it alone, as we decided when we reverted such a change to the instrument word-use query (12%).

R5. Target as narrowly as the shape’s meaning allows

Do. A node shape is run once per focus node (TSD-23), so the number of nodes it targets multiplies everything in it. Target the most specific class that carries the meaning. If the check is global, such as uniqueness within a scheme, consider a constraint on the scheme that reports the offending node as its value, at the price of the report naming the scheme as its focus node. Do not add a SPARQL target (SHACL-AF) to a shape that must also work on a validator without it, since that validator would not select anything and the shape would silently check nothing.

Why. A rule targeting skos:Concept ran 15,713 times in 21 validations of a fixture that merges two vocabularies, and spent 19.9 s of the file’s 22.1 s of SPARQL time on 748 focus nodes each, 415 of which it had a reason to check. R1 cut each run to a seventh and left the count. Scope. pySHACL (the validator runs the constraint per node). Whether other validators batch is not known (TSD-Q14).

R6. Never write a constant FILTER to make a query fail

Do. To make a probe or a test constraint fail, break a triple pattern: $this ex:nothing ?z. Why. rdflib drops a lone constant whose truth value is false (false, 0, "", 0.0), so the query returns every solution, and it inverts NOT EXISTS that contain one (TSD-32). Oxigraph returns no row for a COUNT(*) over a filter it can fold (TSD-33). Scope. a correctness rule for rdflib, and a portability rule for everyone.

R7. Write a negative test for every constraint, and replay every change

Do. A shape with no test that makes it fail cannot be rewritten safely. Exposure’s documentation rule had none until we rewrote it. Before changing a constraint’s query, record the reports the suite produces (§6.3), with mise run dev:record-validations, and compare them afterwards with mise run dev:replay-validations. Scope. everything.

R8. Start from the bound end of a path

Do. A property path with * or +, or a long alternation, written with its unbound end first enumerates from there. Start from the end that is bound or restricted. Evidence: Reasoned, and consistent with the instrument word-use query, where the sections stage (a wrd:directlyComprises* closure) cost 9.5 ms of 18 ms per template. We did not isolate it. Scope. unknown.

4.1 A checklist for a new constraint query

  1. Does it name $this in every pattern that can, so that rdflib runs it bound-first? Is any pattern that tests a bound variable a pattern and not an EXISTS (R1)?
  2. Is any group three or more parts long (R2)? Does any guard sit in the group of an enumeration (R3)?
  3. How many focus nodes will the target have in the largest data the tests build (R5)?
  4. Does a test make it fail, and is its cost per focus node measured on a graph of realistic size (R7, §6)?
  5. Does it use a constant filter, a GROUP BY on $this, or a projection of $this that a text-substituting engine would break (R6, TSD-33)?

5. Rules for the test harness

These concern tools/conftest.py, the test modules and mise.toml, and do not affect the shapes.

H1. Translate each distinct query text once, while pySHACL runs

ValidationCache wraps its call to pySHACL in _sparql_translated_once, which replaces SPARQLProcessor.query for the duration of the call and puts it back. It parses and translates a text the first time and reuses the translated query, which rdflib documents as reusable with different initBindings. The key is the canonical text, the base, and the graph’s bindings for the prefixes the text uses and does not declare (TSD-30). The tree from the first parse is used once, because translation may rewrite it. Gain: 427 s to 128 s. Scope: rdflib. Not when: a test runs SPARQL on rdflib directly, which keeps rdflib’s own behaviour because the replacement is scoped to the one call.

H2. Sort the PREFIX block before keying

_canonical_query sorts the leading declarations, and leaves a text alone that declares a prefix twice. pySHACL writes them in a varying order (TSD-24), and without this the wording tests made 512 parses for 511 texts. Scope: pySHACL.

H3. Parse a fixture once and copy it

Two parses of one document never compare equal as sets, because the parser mints blank nodes (TSD-29). A cache keyed on content therefore cannot hit across parses. Build a fixture once with graph_cache and give each test Graph() + fixture, which keeps the labels. Scope: any parser.

H4. Distribute by test, not by file

check:ontology-catalog runs -n auto --dist worksteal. With loadfile the largest file sets a floor on the run, and on both machines one worker finished 14 s after the median while the others waited. worksteal was 9 to 11% faster and cost 2% more summed time, because each worker parses what it needs. Scope: the harness and pytest-xdist 3.8.

H5. Match the workers to the cores that do real work

PYTEST_XDIST_AUTO_NUM_WORKERS sets what auto means. On R-E, eight workers on four performance and four efficiency cores gave the same wall time as four, and doubled the summed test time (331 s to 640 s), so the efficiency cores added nothing for this workload. Scope: machine. Whether macOS places the workers badly or the chip is power-limited was not isolated.

H6. Keep one reasoner JVM per process, started with a class-data archive

A reasoner call starts a JVM, and starting it and loading the OWL API and HermiT classes was about half of a call. reasoning.run passes -XX:+AutoCreateSharedArchive with an archive beside the jar, which the JVM builds on the first call and rebuilds when the jar changes, with a serial collector and C1-only compilation. A trivial ontology went from 0.54 s to 0.24 s, a typical closure from 1.25 s to 0.70 s, and 41 closures from 51.8 s to 29.9 s. Eight concurrent first runs against a missing archive, six times, all returned the right result and left a valid archive. Scope: JVM. LATTICE_REASONING_JVM_OPTIONS replaces the options.

The archive halves a call and leaves a JVM start in every call. reasoning.run therefore sends its calls to one long-running JVM per Python process, the testkit’s serve command (ADR-A83, addendum of 2026-10-17). A request is one tab-separated line on standard input and an answer is one line of JSON. The JVM keeps the reasoners for its last four distinct closures, keyed by the content of their files, so several questions about one closure load and classify it once. A call that exceeds TIMEOUT kills the JVM and the next call starts another. 41 closures from the tests took 37.7 s with a JVM per call (archive on), 6.3 s on the first pass through one server, and 4.4 s on a second pass. Thirty calls on a small closure took 15.7 s and 0.6 s. The whole suite on four workers took 82 s and 81 s with LATTICE_REASONING_SERVER=0, and 57 s and 54 s with the server. A JVM per worker is the cost. One held 131 MB after its first closure and 242 MB after 41, with four reasoners kept (R-D, resident size from ps), and a closure’s reasoner stays in memory until four newer ones displace it. LATTICE_REASONING_SERVER=0 restores a JVM per call, and a jar built before serve existed makes the process fall back to that by itself.

H7. Check the machine before profiling

A run that is slow on one machine and fast on another is often the machine. Check the power mode, the memory and the load before looking at the code.

Factor What we saw Check
Low Power Mode the same suite took 3.5 times as long with it on (126 s against 36 s) pmset -g \| grep -i lowpowermode
Memory desktop applications held 7.4 of 8 GB with 2.5 GB in the compressor, and the suite adds 1 to 2 GB memory_pressure, vm_stat 5, the profiler’s memory lines

H8. Distinguish a cost from a regression

Compare the commit before a change with the commit after, alternating, twice each, on a quiet machine. A 9 s difference that vanished under that comparison turned out to be another program running on the laptop.

6. Method: how to find a cost and how to change it safely

6.1 Find it

  1. Profile the whole run. mise run dev:time-ontology-tests prints the slowest files and tests, when each worker finished, and the peak memory. Read the worker table first. If the last worker finishes much later than the median, a file-sized chunk sets the wall time (H4).
  2. Profile one slow test with cProfile and read callers, not only totals. A SHACL validation that is mostly parsing (TSD-22) looks different from one that is mostly evaluating.
  3. Count and time per constraint. Wrap SPARQLBasedConstraint._evaluate_sparql_constraint and group by the text without its PREFIX lines. Cost per focus node and the number of focus nodes tell which rule of §4 applies.
  4. Time the parts of the query. Remove its patterns one at a time and time the rest for every focus node, with $this as an initial binding. This is how a type pattern turned out to be half of a rule’s cost (TSD-25).
  5. Check the machine (H7) before believing any of it.

6.2 Reproduce it without our data

benchmark/sparql-constraint-query-cost holds each mechanism as a pair of equivalent queries on synthetic data, on rdflib and Oxigraph. Run it when a rule is doubted, when rdflib or Oxigraph is upgraded, and when a new engine is tried (§7). It fails on a wrong result and never on time.

6.3 Change it safely

  1. Write the claim of equivalence. A rewrite is safe when the two forms mean the same. Say why (the guards read only variables the sub-group binds).
  2. Record, then replay. Run the suite while recording every validation with the shapes as they are, which stores each data graph and its full report. After the rewrite, validate the stored graphs again with the new shapes and compare the reports with blank nodes masked. For wording we replayed 514 validations over 499 distinct data graphs. The tool is tools/validation_replay.py. Record at the commit before the change, mise run dev:record-validations -- --out DIR. Replay at that commit with mise run dev:replay-validations -- DIR --write-baseline FILE, switch to the change, and replay again with --baseline FILE. The replay exits 1 when a validation outside the baseline reports differently. A recording is about 500 distinct validations and takes the time of one suite run, and a replay takes about 40 s on four cores. Breaking the exposure documentation rule on purpose made 22 of them differ.
  3. Compare an unchanged tree first. Replay against the unchanged shapes and note what fails to reproduce (--write-baseline). Four eligibility validations did, because their options (a mix-in ontology) are not recorded, and they differ in the same way after a change, so the second replay subtracts them (--baseline). Two data graphs, which have a literal as a subject, cannot be read back from N-Triples and are counted and skipped.
  4. Add a test that makes it fail (R7), and run the new tests against the old and new shapes. A test that passes only against the new shapes tests the rewrite and not the rule.
  5. Bump the shapes version as the versioning policy says. A rewrite with the same reports is a PATCH, and its tag is the maintainer’s.
  6. Measure with the profiler and compare the constraint’s cost per focus node, not the suite’s wall time, which includes noise.

6.4 Pitfalls we met

  • A reproduction has to be checked against what it stands for. Ours of R3 came out 0.6 times because its guard group bound a variable with many values (discovery record, §7.4).
  • Do not mix a changed README with the old generated file. A test that checks the two agree will fail, and it will look like a behaviour change.
  • A test that pins a current shapes version moves with the version. We left one failing for a commit by running one file after the bump and not the suite.
  • A benchmark’s own pass criterion needs a test that it can fail. That is how TSD-32 was found.

7. If the engine or the validator changes

Change What stays What goes What to repeat

Another SHACL validator on rdflib R1 to R4, R6, R7, H1 R5’s cost model if the validator batches, H2 and H3’s pySHACL parts TSD-23, then the profiler

If a query is run by both engines, as the persistence compiler’s are, write it so that it is correct on both first, and treat the rules of §4 as an optimisation for the engine that needs it.

8. What we have not measured

  • Other engines. Fuseki, Jena ARQ and RDF4J were not run on the benchmark (TSD-Q18), nor was another SHACL validator (TSD-Q14). Every statement in §2 that says “any engine” is a statement of the specification and not of measurement.
  • Why W8 got faster (TSD-Q15) and whether the guard group (R3) always helps when the join is not lazy.
  • inplace=True for pySHACL’s data copy, 9% of a validation here (TSD-Q16).
  • The instrument word-use query. 23 ms per template, half of it in a path closure. We tried an existence rewrite and reverted it for a 12% gain.
  • The wording interval queries. They enumerate candidate points, 132 ms and 82 ms per slot after the guard group. A different formulation of the candidate set could remove the redundant enumeration of the second end, and it would be a change of meaning to check carefully.
  • Efficiency cores. Why they added nothing on R-E.
  • The server’s memory over a long session. We measured one server over 41 closures (242 MB) and the wall time of the suite, and not the memory of eight servers at once on a small machine. The cache holds four reasoners per JVM.

One query per focus node, and the PREFIX order (TSD-23, TSD-24).

import collections, re
import pyshacl
from rdflib import Graph
SHAPES = """
@prefix sh: <http://www.w3.org/ns/shacl#> . @prefix ex: <http://example.org/> .
@prefix owl: <http://www.w3.org/2002/07/owl#> . @prefix xsd: <http://www.w3.org/2001/XMLSchema#> .
ex: a owl:Ontology ; sh:declare [ sh:prefix "ex" ; sh:namespace "http://example.org/"^^xsd:anyURI ] ,
  [ sh:prefix "owl" ; sh:namespace "http://www.w3.org/2002/07/owl#"^^xsd:anyURI ] ,
  [ sh:prefix "xsd" ; sh:namespace "http://www.w3.org/2001/XMLSchema#"^^xsd:anyURI ] .
ex:NeedsNote a sh:NodeShape ; sh:targetClass ex:Concept ;
  sh:sparql [ sh:prefixes ex: ; sh:message "no note" ;
              sh:select "SELECT $this WHERE { FILTER NOT EXISTS { $this ex:note ?n } }" ] .
"""
DATA = "@prefix ex: <http://example.org/> . " + " ".join(f"ex:c{i} a ex:Concept ; ex:note 'n' ." for i in range(40))
texts, original = [], Graph.query
Graph.query = lambda self, q, *a, **k: (texts.append(q) if isinstance(q, str) else None, original(self, q, *a, **k))[1]
shapes = Graph().parse(data=SHAPES, format="turtle")
pyshacl.validate(Graph().parse(data=DATA, format="turtle"), shacl_graph=shapes, advanced=True, inference="none")
print(len(texts), "queries,", len(set(texts)), "distinct text")          # 40 queries, 1 distinct text
orders = collections.Counter()
for _ in range(12):
    texts.clear()
    pyshacl.validate(Graph().parse(data=DATA, format="turtle"), shacl_graph=Graph().parse(data=SHAPES, format="turtle"), advanced=True, inference="none")
    orders[tuple(re.findall(r"PREFIX (\w*):", texts[0]))] += 1
print(len(orders), "distinct PREFIX orders")                           # 2 on pySHACL 0.40.1

Join laziness (TSD-26). Count the lookups with an unbound subject.

import collections
from rdflib import Graph, Namespace
EX = Namespace("http://example.org/")
class Counting(Graph):
    def __init__(self, *a, **k): super().__init__(*a, **k); self.calls = collections.Counter()
    def triples(self, t):
        self.calls[("S" if t[0] is not None else "_") + ("P" if t[1] is not None else "_") + ("O" if t[2] is not None else "_")] += 1
        return super().triples(t)
g = Counting()
for i in range(300):
    g.add((EX.root, EX.has, EX[f"a{i}"])); g.add((EX[f"a{i}"], EX.name, EX[f"n{i}"])); g.add((EX[f"n{i}"], EX.kind, EX.K))
P = "PREFIX ex: <http://example.org/> "
for label, q in (("one pattern", "ex:root ex:has ?a . ?a ex:name ?n . ?n ex:kind ?k"),
                 ("two parts", "ex:root ex:has ?a . { ?a ex:name ?n . ?n ex:kind ?k }"),
                 ("three parts", "ex:root ex:has ?a . { ?a ex:name ?n } { ?n ex:kind ?k }")):
    g.calls.clear(); list(g.query(P + "SELECT ?a ?k WHERE { " + q + " }"))
    print(label, sum(g.calls.values()), "lookups,", sum(v for k, v in g.calls.items() if k[0] == "_"), "with an unbound subject")
# one pattern 601, 0 / two parts 601, 0 / three parts 302, 1
