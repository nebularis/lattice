1. Summary

The question. How should LATTICE support a labelled property graph (LPG) store, queried with GQL or Cypher, as a storage backend?

  • Option 1, compiled native realisation. Explicit configuration in persistence drives a compiler that emits the store schema, one parameterised GQL or Cypher statement per operation, and generated API ingress code in Python, Java and other languages. The runtime is pure LPG.
  • Option 2, SPARQL facade. A new layer implements the SPARQL protocol (and the Graph Store Protocol) over the LPG. It uses the deployment’s persistence configuration to translate each incoming SPARQL request into GQL or Cypher. Everything above the facade keeps speaking SPARQL.

Findings.

  1. Neither option exists without an explicit RDF to LPG mapping, and persistence does not hold one today (fact). dal: records how data is persisted (boundaries, concurrency, ordering, receipts, keys, identity, erasure). It does not record the physical shape of data in a store: which property becomes a node property, which an edge, how a named graph, a datatype or a language tag is represented. Both options need that mapping first, and it is the larger part of the design work in either case (§3).
  2. LATTICE’s runtime uses far less SPARQL than its documentation suggests (fact). The platform reads and writes whole graphs over the Graph Store Protocol and validates them in process. The persistence compiler’s generated SPARQL is executed only by tests, a spike and a benchmark. No production component sends a SPARQL query or update today (§2.2). Option 2’s main benefit, that every consumer keeps speaking SPARQL, protects little that runs.
  3. Option 2’s write path meets the view-update problem (judgement, high confidence). A general SPARQL Update over a schema-dependent mapping has no unique translation. The repository’s own paper on unified SPARQL views (distirbuted-queries.md §3.4) reached the same conclusion for SQL: production virtualisation is read-only, and writes stay native. A facade restricted to the fragment the compiler emits avoids the problem, but it is then Option 1 behind a parser (§5.3).
  4. Option 1 follows the direction already accepted (fact for the decisions, judgement for the fit). ADR-A123 decision 4 makes the compiled profile declare logical resources so that “a relational realisation reads the same declarations and can be compared with this one operation by operation”. The patterns guide’s port (Chapter 25) hides SPARQL behind compareAndSet. The client SDK sketch is the API ingress half of Option 1. An LPG realisation is a second consumer of the same contract.
  5. Option 1 collides with ADR-A75 as drafted (fact). A75 defines the Core tier as “expressible in SPARQL 1.1 + Graph Store Protocol alone”. A pure-LPG adapter cannot be a Core adapter. A75 is still Proposed, so amending it now is cheap. After ratification it is not.
  6. An LPG holds shape-closed instance aggregates well and RDF-native content badly (judgement). The TBox, governed vocabularies, wording documents and triple-grain provenance belong in RDF. This is the same split lattice-sql.md reached for SQL, and it argues for a mixed deployment in which the LPG realisation is chosen per target, not per dataset.

Leaning. Option 1, staged, starting with the mapping vocabulary and an LPG discovery record, then one aggregate family end to end with its graph codec and generated Python and Java ingress. Keep RDF for RDF-native content. Hold Option 2 back, and build a read-only, fragment-bounded facade later only if a named consumer needs SPARQL over LPG-held data (§11). Eight questions for the maintainer are in §10, named LPG-Q1 to LPG-Q8.

2. The scene: what exists today

Every statement in this section was checked against the source named.

2.1 What persistence models, and what it does not

What it is. ontology/persistence/README.md describes the layer as how “one adopter records which options they chose, per class and per deployment, and the tools/persistence compiler turns that record into generated, portable SPARQL and identity minting recipes”. It is a cross-cutting substrate, not a layer in the dependency order, and imports nothing from Foundation through Instrument (ontology-architecture.md §8a).

Targets are a class plus a deployment, discovered through five scope kinds, with a fixed precedence algorithm that refuses ambiguity rather than picking silently (ADR-A78 decisions 2 and 3).

The store is described only by capability. dal:CapabilitySpec carries dal:providesCas, dal:providesReasoning, dal:providesCommitValidation, dal:providesSingleWriter and dal:providesStatementLevelConflictDetection (persistence.ttl lines 289 to 311). Its comment says it shares its field shape with the patterns guide’s StoreCapabilities record “by design, not by identity”. There is no backend kind, no dialect and no physical mapping anywhere in dal:.

What the compiler emits. compile produces a dal:CompiledProfile graph and no SPARQL text. instantiate turns it into SPARQL, and export-recipes into minting recipes (tools/persistence/README.md, ADR-A79). Since ADR-A123, each operation is a typed value built by a builder and rendered by one renderer. Two details of A123 matter here.

  • Decision 4. The compiled profile names “logical resources (the aggregate with its members, its version row, the transaction claim, the receipt, a key claim, a log bucket), not SPARQL graph roles”. The builders map each logical resource to a graph role. “A relational realisation reads the same declarations and can be compared with this one operation by operation.”
  • The IR itself is SPARQL-shaped. persistence/ir.py builds patterns inside a GraphBlock that names a GraphRole, and a property path holds its rendered SPARQL text (A123, third addendum). Another realisation reuses the logical contract, not the IR.

The SPARQL fragment the operations rely on (A123 decision 2, the patterns guide, and the generated operations): named graphs in every pattern and never the default graph, DELETE/INSERT/WHERE, FILTER NOT EXISTS, OPTIONAL, property paths in WHERE only (the composite sweep), BIND with IRI, CONCAT, STRDT, ENCODE_FOR_URI, NOW() outside guards, VALUES, typed literals (xsd:long positions), and DATATYPE tests in parameter guards. No blank nodes.

A pending decision bears on both options. PDD-06 proposes a second IR that models SPARQL’s semantics between the configuration IR and the text, and notes that “a relational backend then needs its own path or IR”. An LPG backend is in the same position.

3. The gap both options share: an RDF to LPG mapping

Option 1 needs the mapping to generate schema, statements and the graph codec. Option 2 needs it to translate each SPARQL request. The mapping is the same object in both, and this section is common ground.

3.1 Where the two models disagree

RDF LPG (GQL, Cypher) Consequence for a mapping
a resource is identified by an IRI, globally a node has an internal, store-local id an iri property with a uniqueness constraint on every mapped node. Identity stays with the minting recipes
rdf:type, any number of classes a set of labels on a node labels for asserted types. Inherited types are either materialised as extra labels or not, so a query for a superclass finds nothing unless they are
a literal-valued property, any multiplicity a single-valued node property, or a homogeneous list sh:maxCount 1 maps to a scalar property. Unbounded multiplicity maps to a list, which adds order and allows duplicates, or to separate value nodes
an IRI-valued property a relationship direction and type follow the predicate. An inverse property becomes a reversed traversal, not a second edge
a triple exists or does not (set semantics) relationships have identity, and two parallel relationships of one type are allowed every write needs MERGE or a uniqueness guard to keep set semantics
a statement about a statement needs reification or RDF 1.2 triple terms relationships carry properties natively a qualified relation can become an edge with properties, but only where the mapping says so. Going back to RDF needs the reification pattern fixed in the mapping
a predicate is itself a resource, with its own triples a relationship type is a name statements about properties (rdfs:subPropertyOf, fnd:utility) stay in the TBox, outside the LPG

xsd:decimal, exact no exact decimal in Neo4j’s Cypher type system (verify). GQL defines exact numeric types, with uneven support (verify) money and quantities (Quantification) need a rule: scaled integer, string with a declared scale, or a float, which is wrong for money
xsd:dateTime with or without a time zone zoned and local date-time types are distinct (verify for each store) a better fit than most RDF stores, provided the mapping keeps the distinction
language-tagged strings no language tag a map {value, lang}, a property per language, or value nodes. Each changes how LANGMATCHES and per-language lookup work
blank nodes nodes without an IRI skolemise on write. A123 already forbids blank nodes in payloads. Addresses and similar structured values in other layers may still use them
rdf:List a list property, or a chain of nodes a list property for literals, ordered relationships for resources
named graphs, quads no named graphs in one database. GQL has a catalogue of graphs, Neo4j has databases (verify) a mapping rule is required (§3.3)
open world, absence means unknown absence is usually read as false or null evaluation of Eligibility’s three values must not turn Undetermined into Denied through null handling (the same hazard lattice-sql.md §3.5 records for SQL)

3.2 Two families of mapping

Schema-independent (generic). Every resource becomes a node, every literal becomes either a property keyed by predicate IRI or a literal node, every triple between resources becomes an edge whose type is the predicate IRI. It preserves all information for any graph, and it throws away everything an LPG is good at. Queries become generic edge walks with string-typed relationship names, and no schema constraint can be stated.

Schema-dependent (shape-driven). Closed SHACL shapes with bounded multiplicity determine node labels, scalar properties and relationship types. It produces a natural LPG with native constraints, and it applies only to data that conforms to closed shapes. lattice-sql.md §3.2 calls this the “compilable fragment” for SQL. The same fragment applies here, with fewer restrictions, because an LPG tolerates optional properties and multiple labels where SQL needs nullable columns or extra tables.

The published work on this mapping (verify each):

  • Angles, Thakkar and Tomaszuk, Mapping RDF databases to property graph databases, IEEE Access,
    1. Defines schema-independent and schema-dependent mappings with information preservation and query preservation (SPARQL to Cypher for the preserved fragment).
  • Rabbani, Lissandrini, Bonifati and Hose, S3PG, SHACL-driven transformation of RDF to property graphs, around 2024. Closest in spirit to LATTICE’s shape-first design.
  • Neo4j’s neosemantics (n10s) plugin imports RDF under configurable rules (how to shorten IRIs, how to treat multi-valued properties, types as labels or nodes, keep language tags or custom datatypes) and exports RDF from Cypher results. It offers no SPARQL endpoint.
  • G2GML and PG-Schema on describing property graph schemas and graph-to-graph mappings.

Judgement. LATTICE should use a schema-dependent mapping for persistence-managed aggregates, generated from the boundary shapes the persistence configuration already requires (dal:boundaryShape, ADR-A122), with explicit refusals for what falls outside the fragment. A generic mapping is worth having only as a fallback for small, rarely queried long-tail data, and even then an RDF store is the simpler home for it.

3.3 Named graphs

The persistence operations use graph roles everywhere (payload, meta, keys, transaction, log buckets, events, registry, and for some models deltas and snapshots), and ADR-A122 decision 8 makes the named-graph IRI injective in the aggregate root. The runtime reads by graph IRI. A mapping has four choices.

Choice How Good for Breaks
G1, a graph property on every node and relationship _g holds the graph IRI a faithful round trip of a graph read one IRI that occurs as a subject in two graphs with different property values. The node is shared, its properties are not per graph
G2, a node per (graph, IRI) pair node identity includes the graph exact quad semantics cross-graph joins on the same IRI, which every persistence guard performs (version row, keys, transaction claim)
G3, a database or catalogue graph per graph one physical graph each strong isolation, per-tenant datasets (ADR-A54) per-aggregate graphs, which can number millions, and atomic writes across graphs
G4, logical resources mapped natively the aggregate is the subgraph owned by its root, the version row is properties on the root or a :VersionRow node, claims are nodes with uniqueness constraints the persistence operations, which ADR-A123 already states in logical resources reading an arbitrary named graph by IRI, unless the codec reconstructs it

Judgement. G4 for everything persistence manages, with a generated codec that reconstructs the graph named by a GraphReference from the aggregate’s subgraph and returns canonical N-Quads, so ScopedDataset.read and the revision hash keep working (ADR-A30). G3 at the tenant or dataset level only. G1 and G2 only inside a generic fallback.

3.4 Where the mapping lives

The mapping is configuration of the same kind as dal:, chosen per deployment and per target, and it is shared in part with a relational realisation (both decide scalar versus reference, how a datatype is stored, how a key is enforced). Three homes are plausible, and this is LPG-Q2.

Home For Against
M-A, new terms in dal: one configuration, one resolver, one precedence algorithm. dal: already exists “to decide how its data is stored” dal: is defined as backend-neutral selection of patterns. Physical mapping is a different concern and would grow it substantially
M-B, a new cross-cutting module beside persistence, Surface and MORK, shared by SQL and LPG realisations separates “which pattern” from “which physical shape”. One mapping vocabulary serves both realisations a new ontology module and a new kind of directory, so an ADR under A77, plus versioning under A86
M-C, deployment configuration outside the ontology, for example JSON quick to start breaks “configuration is canonical RDF” (A78, A79), and no SHACL validates it

4.5 The graph codec

ScopedDataset.read(GraphReference) must return the graph named by an IRI as canonical N-Quads with a content hash, because the hash travels in every cross-runtime reference (ADR-A30). On an LPG target the platform adapter rebuilds the graph from the subgraph the mapping assigns to that IRI.

Three properties must hold, and each needs a test.

  1. Round trip. For data in the fragment, writing RDF through the mapping and reading it back returns the same graph.
  2. Hash agreement. The same logical content gives the same hash on the RDF and the LPG realisation. This fails if the stores keep different lexical forms, for example 4200.00 in Fuseki and a canonical 4200.0 rebuilt from an LPG number. Either the mapping stores the lexical form, or both realisations canonicalise literals at write time.
  3. Determinism. The same subgraph always gives byte-identical output, with stable ordering and no store-assigned ids in it.

Revisions are immutable, so a codec result can be cached by revision hash.

4.8 Assurance

  • Differential testing across realisations. The same logical operation on the RDF realisation (rdflib, Oxigraph, later Fuseki) and on the LPG realisation must give the same logical outcome and the same codec output. ADR-A123’s consequences warn that two realisations generated from one contract share any misreading of it, so Track H’s H5 models stay the independent oracle.
  • A port-level TCK. The guide’s TCK (Chapter 27) asserts behaviour, for example “exactly one claim” after 64 threads race on one key. Restated against the logical port instead of SPARQL text, it runs against every realisation.
  • Mapping laws. Round trip, hash agreement and determinism (§4.5), as property tests over the fixtures of each substrate layer.
  • Injection. Values travel as native query parameters, which is stronger than today’s text substitution. Labels, relationship types and property keys cannot be parameters in Cypher (verify for the chosen dialect and version), so they are compile-time constants passed through an identifier encoder with its own adversarial corpus, as ADR-A79 decision 5 requires for terms.

5.3 The write path and the view-update problem

A SPARQL update speaks in triples. A schema-dependent mapping stores entities. Translating a set of triple insertions and deletions into entity changes has zero, one or several valid answers, which is the view-update problem that distirbuted-queries.md §3.4 records for SQL (Bancilhon and Spyratos, 1981, Dayal and Bernstein, 1982). 5.4 Why the fragment-bounded facade is Option 1 in disguise

The persistence operations are a small, known set (about seventeen kinds, each a typed value with declared parameters and derived read and write sets, ADR-A123 decisions 1 to 4). A facade that handles only them must recognise each one from its SPARQL text and apply the LPG statement for it. That LPG statement has to be written per operation, exactly as in Option 1. What F-B adds is a parser and a recogniser in the request path, and a dependence on the SPARQL text staying recognisable as Track H changes it. What it buys is a SPARQL-speaking endpoint that passes the same TCK and satisfies ADR-A75 as drafted.

5.5 The read path

Appendix B lists every construct. The gaps that matter most:

  • Variable predicates. ?s ?p ?o must range over properties, labels and relationship types at once, as a union of three different access paths. LATTICE’s own sweeps use it.
  • Term semantics over LPG values. DATATYPE, LANG, STR, isLiteral, sameTerm and term-level pattern matching (4200.00 against 4200.0) need the RDF term, which the LPG does not store unless the mapping keeps lexical forms and datatypes. The persistence parameter guard, DATATYPE($p) = DATATYPE("0"^^xsd:long), is one such test.
  • Errors versus nulls. SPARQL removes a row whose filter errors, and !error is still an error. Cypher’s null logic removes the same rows in most cases. Where it differs, for example in COALESCE, equality across types (1 = "1" is false in Cypher, an error by the letter in SPARQL), aggregates over mixed types and the ordering of mixed kinds, the facade must emulate SPARQL.
  • Path semantics. SPARQL’s * and + return each reachable node once. Cypher’s variable-length patterns return paths under relationship-isomorphism, so duplicates need DISTINCT. An arbitrary regular path expression, such as the state-eliminated owned path of ADR-A122, needs quantified path patterns (verify the version that supports them). Zero-length paths already differ between two RDF stores (TSD-08).
  • Named graphs. GRAPH ?g must invert the mapping’s graph rule. Under choice G4 that means inverting ADR-A122’s graph IRI template, which is injective and so possible.

  • A general SPARQL endpoint is a new network surface. Property paths and cross products make query-cost denial of service easy, so the facade needs cost limits and timeouts.

10. Questions for the maintainer

LPG-Q1. What need drives LPG support? (a) An LPG as system of record for some instance aggregates. (b) Traversal, graph algorithms or visualisation over data that RDF keeps. (c) Both. Consequence: (b) is served by V3 with far less work and no change to ADR-A75. (a) needs Option 1 or 2. Leaning: ask first, because the answer can remove most of this document’s scope.

LPG-Q2. Where does the RDF to LPG mapping live? (M-A) new terms in dal:. (M-B) a new cross-cutting module beside persistence, Surface and MORK, shared with a relational realisation. (M-C) deployment configuration outside the ontology. Leaning: M-B, because physical mapping is a separate concern from pattern selection and SQL needs the same module. It costs an ADR.

LPG-Q3. Which option, and if Option 2, which scope? (1) Option 1. (2-A) a general facade. (2-B) a fragment-bounded facade. (2-C) Option 1 plus a read-only facade later. Leaning: (1), with (2-C) held until a consumer needs it. Reasons in §11.

LPG-Q4. How does ADR-A75 accommodate a non-SPARQL backend? (a) Restate the Core tier as the logical port (read by reference, compareAndSet, resolve), with SPARQL and the Graph Store Protocol as the RDF realisation of it. (b) LPG adapters form a second SPI family outside the three tiers. (c) Leave A75 as drafted, and only Option 2 is possible. Leaning: (a), decided before A75 is accepted, since a superseding ADR later is costlier.

LPG-Q5. Which store and dialect first? (a) Neo4j and its Cypher. (b) an openCypher store such as Memgraph. (c) ISO GQL syntax wherever the chosen store supports it. Each choice also fixes an edition and a licence for tests (verify). Leaning: one concrete store with mature Java and Python drivers and a container image for tools/testing/, written in GQL-conformant syntax where the store allows, so a second store is a capability-record change more than a rewrite.

LPG-Q6. Ingress languages, form and home? (a) Python and Java, sketch option S-B, under packages/, one SDK serving RDF and LPG targets. (b) per-backend SDKs. (c) defer ingress, ship statements and a written runtime only (S-A). Leaning: (a), with outcome classification behind an interface until H5 and H6 settle it.

LPG-Q7. Must graph-reference hashes agree across realisations? (a) Yes. Literals are canonicalised at write time in both realisations. ADR-A123 decision 6’s canonical N-Triples payload is a start. (b) No. A hash is per realisation, and a reference names its realisation. Leaning: (a), because a reference that changes meaning with the store breaks ADR-A30’s contract.

LPG-Q8. Is the realisation chosen per target or per deployment? (a) Per target, so one deployment can hold RDF families and LPG families, with cross-store work as sagas. (b) Per deployment, one store for everything persistence manages. Leaning: (a), which matches how dal: already resolves every other dimension per target, and keeps RDF-native content in RDF.

11. Leaning

Option 1, staged. The reasons, in order of weight:

  1. The runtime does not need SPARQL over the store today. The platform moves whole graphs by reference and computes in process (§2.2). Option 2’s central benefit protects consumers that do not exist yet.
  2. The write path decides it. A general facade cannot translate SPARQL Update faithfully over a mapping that makes the LPG worth having (§5.3). A facade that only accepts the compiler’s operations is Option 1 with a parser in the request path (§5.4).
  3. The architecture already points this way. ADR-A123 decision 4 made the logical contract the thing a second realisation reads. The patterns guide’s port and capability record are store properties, not SPARQL properties.   4. The cost of the conflict with ADR-A75 is lowest now, while A75 is Proposed (LPG-Q4).
  5. Assurance is bounded. Option 1’s correctness is seventeen operations, a codec and a mapping, checked against the RDF realisation and Track H’s models. Option 2’s is a SPARQL engine’s.

Appendix A: one operation through both options

A composite replace on a claim aggregate whose boundary shape owns lines and notes. The statements below are simplified illustrations of shape, not generated output.

The logical contract (ADR-A123 decision 4). Parameters root (Iri), epoch (Long), expectedSeq and nextSeq (Position), newRev (Iri), txnId (Iri), requestDigest (Digest), payload (Payload, ground triples reachable from root by owned edges). Reads the aggregate with its members, the version row and the transaction claim. Writes the aggregate, the version row, the transaction claim and a receipt.

Today’s SPARQL shape, simplified:

DELETE {
  GRAPH <urn:g:data>    { ?s ?p ?o }
  GRAPH <urn:g:meta/17> { $root pat:seq $expectedSeq ; pat:head ?oldHead }
}
INSERT {
  GRAPH <urn:g:data>    { } }
  GRAPH <urn:g:meta/17> { $root pat:seq $nextSeq ; pat:head $newRev }
  GRAPH <urn:g:txn>     { $txnId pat:digest $requestDigest ; pat:revision $newRev }
}
WHERE {
  { FILTER(isIRI($root) && DATATYPE($expectedSeq) = DATATYPE("0"^^xsd:long)) }
  GRAPH <urn:g:meta/17> { $root pat:epoch $epoch ; pat:seq $expectedSeq ; pat:head ?oldHead }
  FILTER NOT EXISTS { GRAPH <urn:g:txn> { $txnId pat:digest ?anyDigest } }
  OPTIONAL { GRAPH <urn:g:data> { $root (ex:hasLine|ex:hasNote)* ?s . ?s ?p ?o } }
}

Option 1, a Cypher statement of the same operation, illustrative. The locking idiom and clause behaviour are what probes P-L1 and P-L2 must confirm (verify).

// Parameters: $root, $epoch, $expectedSeq, $nextSeq, $newRev, $txnId, $requestDigest,
// $rootProps, $lines, $notes  (the payload, already checked against the boundary shape)
MATCH (r:Claim {iri: $root})
SET r._lock = true                               // take the write lock before reading the version
WITH r
WHERE r.epoch = $epoch AND r.seq = $expectedSeq
  AND NOT EXISTS { MATCH (:TxnClaim {id: $txnId}) }
OPTIONAL MATCH (r)-[:HAS_LINE|HAS_NOTE*1..]->(m)
WITH r, collect(DISTINCT m) AS members
FOREACH (m IN members | DETACH DELETE m)
SET r = $rootProps, r.iri = $root, r.epoch = $epoch, r.seq = $nextSeq, r.head = $newRev
FOREACH (l IN $lines | CREATE (r)-[:HAS_LINE]->(:ClaimLine {iri: l.iri, amount: l.amount}))
FOREACH (n IN $notes | CREATE (r)-[:HAS_NOTE]->(:ClaimNote {iri: n.iri, text: n.text, lang: n.lang}))
CREATE (:TxnClaim {id: $txnId, digest: $requestDigest, revision: $newRev})
CREATE (:Receipt {target: $root, seq: $nextSeq, revision: $newRev, txn: $txnId})
RETURN 1 AS applied

No row means the guard failed, and the generated ingress classifies the outcome by reading the transaction claim, as the guide’s resolve does. The uniqueness constraint on TxnClaim.id makes a resend a refusal, not a second write. Labels, relationship types and property keys are compile-time constants from the mapping. Every value is a parameter.

Option 2, scope F-A, receiving the SPARQL above. The facade must, at runtime:

  1. parse the update and substitute nothing, since the caller already substituted text
  2. evaluate the guard group over constants, emulating DATATYPE on an xsd:long literal
  3. map GRAPH <urn:g:meta/17> to the version properties on the root node, which needs the meta graph role in the mapping, and recognise that pat:seq, pat:head and pat:epoch are properties of the root, not of a separate meta resource
  4. map FILTER NOT EXISTS { GRAPH <urn:g:txn> ... } to an existence test on TxnClaim
  5. evaluate the optional sweep, turning the path into a pattern over the owned relationship types, and ?s ?p ?o into every mapped property, label and relationship of every member, as triples
  6. instantiate the DELETE template into triple deletions, and each into a property removal, a label removal or a relationship deletion
  7. instantiate the INSERT template into triple insertions, group the payload triples by subject, rebuild entities, choose labels from rdf:type triples, and decide which pairs of a deleted and inserted pat:seq triple are really one SET
  8. check the end state against the mapping, then commit, all in one transaction

Steps 3, 6 and 7 rediscover at runtime, from triples, what the compiled profile states outright.

Appendix B: SPARQL construct by construct

What a general facade (scope F-A) must emulate, against GQL or Cypher. “Gap” is the semantic distance, judged against the SPARQL guide in .local/sparql-guide.md and the specification.

SPARQL Nearest GQL or Cypher Gap
BGP with fixed predicates MATCH over nodes, properties and relationships per the mapping small for mapped predicates
variable predicate ?p a union over properties (keys(n)), labels and relationship types large. Three access paths and string-typed results
a / rdf:type label tests small for asserted types. Inherited types need materialised labels or a closure
literal matched as a term property equality on a value medium. Lexical form, datatype and language tag are gone unless the mapping stores them
blank nodes in a pattern anonymous pattern nodes small
FILTER, effective boolean value WHERE medium. EBV of strings and numbers differs from Cypher truthiness
errors and \|\|, && null and three-valued logic medium. Same rows removed in most filters, different in COALESCE, IN, equality across types
OPTIONAL, with its own filter OPTIONAL MATCH ... WHERE small to medium. Nested optionals and filters referring outward need care
UNION UNION ALL with null padding to equal columns small
MINUS an anti-join with the shared-variable rule medium. No direct construct
EXISTS, NOT EXISTS existential subqueries small to medium. Substitution semantics
BIND WITH ... AS small. Scope rules differ
VALUES, UNDEF UNWIND of parameter lists with nulls small. UNDEF must act as a wildcard in the join, which null does not
