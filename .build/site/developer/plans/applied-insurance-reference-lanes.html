Applied Insurance Reference — Machines, Branches and Merges

Epic: applied-insurance-reference Purpose: which machine and agent builds each slice, on which branch, in which round, and who merges what. Slice content stays in the phase plans. Revised 2026-10-13. Machine S builds its slices in sequence, so they share one long-lived branch, air/applied-reference, instead of one branch each. The per-slice air/<slice> branches of rounds 1 to 3 were all merged into main and are deleted (§3). Machine R’s own slices still take their own branches.

Revised again 2026-10-13: one trip. Every AIR slice that does not wait on CCS or NRS is built on S in one trip, and the branch comes to R once, when the trip is done (§4). The reasons:

  • Versioning (ADR-A86) governs what is released on main. A branch is not a release, so the branch carries one bump per document whatever the number of slices that change it, and its imports stay pinned to the layer versions of main at the branch point while CCS moves on.
  • An applied module is not substrate. Nothing on main imports the AIR modules except other AIR modules, so main loses nothing while they wait on the branch.
  • Every brief for the trip is written before S starts (§1, “Brief before start”), so S needs nothing from R mid-trip.

R re-pins the branch to main’s layer versions once, at the merge (§6 step 4).

1. Machines and agents

Machine Can Cannot Agents Used for
R, runtime run mise, Python, Java, every check. Push to GitHub. Merge — Claude Code, Copilot Pro+ Claude: compiler and substrate code, ADRs, verifying design-heavy branches. Copilot Pro+: running a branch’s checks and fixing simple failures
S, sandbox edit anything, commit, pull from GitHub, run mise and every repository check locally (confirmed durable 2026-09-29) push Copilot Business (the largest budget) Turtle, SHACL, examples, READMEs, and code of any complexity, since S now verifies its own work before handoff. Push, merge, catalog regeneration and release tagging stay on R regardless of what S can run

These rules follow:

  • The maintainer runs the branching and merging. Agents must not run the git commands this plan gives for creating, switching, fetching, pulling, pushing, bundling, rebasing or merging branches (§3, §6). They may run any other local git command their normal workflow needs, such as git status, git diff, git log or committing on the branch the maintainer has checked out. When a step needs one of the maintainer’s commands, the agent stops and says so. The one exception: machine R’s agent may run them when we explicitly ask it to. Machine S’s agent never does.
  • Branches are created, pushed and merged on R only. S pulls, works and hands its commits back as a bundle (§3). S’s agent commits on air/applied-reference and nowhere else.
  • Brief before start. S starts a slice only once its brief is on air/applied-reference: an “in detail” section in its phase plan and a Validation Pack skeleton. Every brief of the trip is on the branch when it is created, so S builds the whole trip without a sync. If S finds a brief wrong or incomplete, it stops at that slice, records the question in the slice’s Validation Pack and its own status section, and goes on with the next slice that does not depend on the answer. Whenever machine R’s agent reports what comes next, it ends with exactly one of these, on its own line:
    • 🔴 PLAN FIRST: AIR-x.y needs its brief drafted before the trip. It lists every such slice, and R drafts them before anything else.
    • 🟢 READY TO BRANCH: create and push <branch>, … It names a branch only when one is due, which is now only R’s own slices (AIR-3.3, AIR-3.5, substrate). S’s work needs no new branch.
  • One commit range per slice. Each slice is a contiguous run of commits whose messages start [AIR-x.y]. The last one is the handoff commit, [AIR-x.y] Handoff, which carries the Validation Pack’s Handoff section and the slice’s state in the status record. Commits carry the trailer GENAI_CONTRIBUTION.md requires.
  • Bump each document once on the branch. The release register has a row only for a document’s current version on main (tools/ontology_releases.py write), and the trip merges whole. The first slice that changes a document bumps it under ADR-A86, classified by the change the whole trip makes to it, and later slices change its content without changing owl:versionIRI. A later slice that turns a MINOR into a MAJOR raises the one bump and says so in its Handoff. New documents start at 0.1.0 and stay there until the merge. Imports of LATTICE layers stay pinned to the versions of main at the branch point, and S never re-pins them.
  • S verifies its own slice before marking it handed over. Run the Validation Pack’s single command, plus mise run check:ontology-catalog and mise run check:ontology-versioning when the slice touches ontology/, and record the result in the Validation Pack’s Handoff section. If a specific check cannot run in S’s environment (for example, a dependency that will not resolve even through the configured package mirror), name exactly which command and why, so R knows to run that one first. S still cannot regenerate catalogs or create release tags, so it bumps owl:versionIRI literals and .version files by hand under ADR-A86 as before.
  • R re-verifies as the merge gate, not as the first run. Because S already ran the checks, R’s run should confirm rather than discover. A failure at this stage that S’s own run did not catch is worth a note in the Validation Pack — it usually means environment drift between S and R, not a routine defect.

3. The round trip for the S branch

Every command in this section is run by a maintainer. Machine R pushes to the origin-ssh remote (SSH avoids GitHub’s HTTP authentication). Machine S only fetches, from origin.

Once: create the branch and delete the old ones

On R, from a main that holds the plan documents of this revision:

git switch main && git pull --ff-only

git switch -c air/applied-reference && git push -u origin-ssh air/applied-reference

The eight per-slice branches of rounds 1 to 3 are all ancestors of main, so -d deletes them and refuses anything that is not:

git branch -d air/1.1-layout air/1.2-shared-contracts air/2.1-peril-spec air/2.2-characteristics air/3.1-flat-hierarchy air/3.2-set-readings air/3.3-readings-swrl-owl air/4.1-exposure-core

git push origin-ssh --delete air/1.1-layout air/1.2-shared-contracts air/2.1-peril-spec air/2.2-characteristics air/3.1-flat-hierarchy air/3.2-set-readings air/3.3-readings-swrl-owl air/4.1-exposure-core

The branch is pushed before S starts, so S can fetch it.

The trip

On S, the first time, take the branch:

git fetch origin && git switch -c air/applied-reference --track origin/air/applied-reference

The agent reads the status record, then builds every slice of the trip in sequence order (§4, §5). It verifies each slice before its handoff commit: the Validation Pack’s single command, plus the ontology catalog and versioning checks if the slice touches ontology/. It records the result in the Validation Pack’s Handoff section. A pass here means R’s later verification confirms rather than discovers. A slice blocked on a question is skipped as §1 says, and the agent comes back to it when the question is answered.

S never fetches main during the trip and never merges it into the branch. The branch is self-consistent at its branch point, and R brings it up to date once, at the merge (§6).

The trip is long, so S may write a backup bundle whenever it likes, with the bundle command below. A backup stays on S. It is not carried to R and nothing is merged from it.

On S, bundle the trip:

git fetch origin && git bundle create air-trip.bundle origin/air/applied-reference..air/applied-reference

Carry the file to R. One bundle holds every slice of the trip, so the physical handoff happens once.

On R, take the commits and push them:

git switch air/applied-reference && git pull --ff-only /path/to/air-trip.bundle air/applied-reference && git push origin-ssh

Then verify each slice in order, and merge the trip (§6). S makes no commit on the branch after it bundles. If R returns slices that failed their gate (§6 step 2), the maintainer refreshes S with git fetch origin && git merge --ff-only origin/air/applied-reference and S fixes them on the branch as a short second trip.

5. Tracking progress: the status record

The status record is the single record for the epic. No per-phase status records are created. It has one section per machine, so the two machines’ edits never touch the same lines:

Section Written by Content
Round R the current round, the trip’s slice order, and the briefs on the branch
Machine R R position, blockers, R’s slice board, the queue of S slices awaiting verification
Machine S S position, blockers, S’s slice board
Merge log, Phases R one row per merged slice, and each phase’s state

A slice moves through these states. The machine named in the last column sets each one:

State Meaning Set by
waiting a slice it starts after is not yet built —
waiting for brief its brief is not yet on the branch R, when it drafts the brief
ready its brief is on the branch and the slices it starts after are built R, when it writes the brief, or S, when it finishes the slices it starts after
in progress the agent is building it the building machine
handed over S’s handoff commit exists and we have bundled it to R S
built R’s own work is committed and ready to verify R
verifying R is running its checks (§6) R
gate passed the maintainer has run the validation gate and recorded the adversarial probe in the status record R
merged it is on main, with a row in the merge log R

Handoff notes go in the Validation Pack, docs/developer/validation/applied-insurance-reference-<slice>.md, which each slice creates. The building machine adds a “Handoff” section: what it built, what it ran and could not run, and anything R should check first. Keeping these notes out of the status record keeps S’s commits and R’s apart.

At the start of a session, an agent reads the status record on its checked-out branch, then its slice’s phase plan and Validation Pack. At the end of each slice, it updates its own section (position, the slice’s state, blockers) in the slice’s handoff commit. Machine S never edits the Round, Machine R, Merge log or Phases sections. R edits them on the branch after taking S’s bundle, so the two machines’ commits never touch the same lines. When a merge of main conflicts in the status record, keep each section’s newest version. The sections are disjoint, so this never loses information.

6. Verifying and merging on R

For the trip, once S’s bundle is on the branch (§3):

  1. Verify each slice at its handoff commit (agent). Check out the slice’s [AIR-x.y] Handoff commit and run the same commands S already ran: the Validation Pack’s single command, plus mise run check:ontology-catalog and mise run check:ontology-versioning when the slice touches ontology/. This confirms S’s recorded result, unless S’s Handoff section named a check it could not run, in which case R runs that one for the first time here. Then run the same commands at the branch tail.
  2. Fix failures (agent). Copilot Pro+ first for simple ones. Claude when the fix needs a design judgement. Fixes are new commits on the tail, [AIR-x.y] Fix …, and every slice a fix touches is verified again. A failure that S’s own self-verification passed is worth flagging as environment drift. If a failed slice cannot be fixed in the trip, R merges the verified prefix of the trip and returns the rest, re-bumping versions where step 4 applies.
  3. Sync with main (maintainer, then agent). The maintainer runs git switch main && git pull --ff-only && git switch air/applied-reference && git merge main. The branch is never rebased and never force-pushed, because S fast-forwards to it. The agent helps resolve conflicting files. This happens once, after the trip’s slices are verified at their handoff commits.
  4. Re-pin once (agent). The branch’s imports are pinned to the layer versions of main at the branch point (§1). Re-pin every applied module the trip changes to the current versions on main, and if main has bumped a document the trip also changes, take main’s version and bump once more under ADR-A86. Run each slice’s Validation Pack command again at the tail, since the newer layers may break a test. Commit it as [AIR] Re-pin ….
  5. Regenerate catalogs and release rows (agent). mise run build:ontology-catalog, and after any version bump mise run build:ontology-releases, which adds a row to docs/architecture/ontology-releases.md for each new version and lists the tags to create. Commit the result on the branch, then run the trip’s checks once more.
  6. The validation gate (maintainer). For each slice, in order, the maintainer reviews the pack, runs its command, inspects the artefacts and sets one adversarial probe. The agent breaks the implementation, shows the test fails, restores it, and records each probe and its result in the status record. The maintainer’s merge is the sign-off.
  7. Record (agent). On the branch: each slice’s state becomes merged, a merge log row is added per slice, and the epic’s INDEX.md entry is updated.
  8. Merge (maintainer). git switch main && git merge --ff-only air/applied-reference, then git push origin-ssh main. Create the release tags step 5 listed and push them to origin-ssh. The branch is deleted after the merge, unless a second trip is due (§3).

The handoff ends with 🔴 RELEASE TAGS REQUIRED while tags remain to create (the lifecycle skill).
