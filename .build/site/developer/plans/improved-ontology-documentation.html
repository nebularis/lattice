Plan: Literate specifications, the repository catalogue, and published documentation

Unit ID: improved-ontology-documentation (slice prefixes OD, RC and DOC, questions OD-Qn) Status: Planned, rewritten 2026-10-16 after the design discussion of 2026-10-15 and 2026-10-16. Not started. Every design question is answered. Branch: docs/literate-v2 Sketches: improved-ontology-documentation.md, repository-catalogue.md, which this unit absorbs Status record: improved-ontology-documentation.md ADRs to draft as Proposed (OD0): A121 Repository catalogue, A126 Literate specification layout and grammar (with an addendum to ADR-A120), A127 Published architecture decisions. A121 is the number the catalogue sketch reserved. Every number is re-checked against the catalogue before filing. The last slice needs a further ADR that supersedes part of ADR-A88. Constraints kept: ADR-A86 and the versioning policy are unchanged (generated Turtle stays tracked and versioned). Examples stay hand-written and committed first (ADR-A-C2).

What we are building

  1. One layout for every module README, whose normative sections are compiled to Turtle and SHACL from a markdown grammar, so a term’s axioms are written once. turtle-spec blocks remain only for what the grammar cannot say.
  2. The repository catalogue, with each module’s entry in its own README (section 3) and one root file for the rest, read by one module that every tool uses.
  3. A sources discipline for user-facing documentation, and a site built from declared sections. READMEs, generated Turtle and user guides never refer to working documents, and cite only published ADRs.

The section 6 grammar

Everything is line-based so the extractor stays standard-library only. An entry is a #### heading holding one CURIE, followed by labelled paragraphs and tables. An unknown label is an error.

Label Applies to Produces
**Definition.** every term, required rdfs:comment
**Utility.** every term fnd:utility
**Label.** every term rdfs:label
**Subclass of.** class rdfs:subClassOf, one per comma-separated Manchester expression
**Equivalent to.** class owl:equivalentClass, one Manchester expression
**Key.** class owl:hasKey
**Restrictions.** class the restriction table below
**Domain.**, **Range.** property rdfs:domain, rdfs:range, Manchester expressions (A or B gives a union)
**Characteristics.** property functional, inverse functional, transitive, symmetric
**Inverse of.**, **Subproperty of.** property owl:inverseOf, rdfs:subPropertyOf
**Scope note.** and further labels any term the matching annotation property (OD-D12)

The restriction table has the columns Property, Values, Asserted in and Message. Values is the body of a Manchester restriction:

Values OWL SHACL, when asserted there
exactly n, min n, max n owl:cardinality, minCardinality, maxCardinality sh:minCount, sh:maxCount
exactly n C, min n C, max n C the qualified forms with owl:onClass sh:qualifiedValueShape [ sh:class C ] with the qualified counts
only C owl:allValuesFrom sh:class or sh:datatype
some C owl:someValuesFrom a qualified minimum of 1
value v owl:hasValue sh:hasValue
anything nested the expression refused unless the row says OWL only

A blank Asserted in cell means OWL and SHACL. Generated SHACL goes into one <Class>Shape per class in the module’s structural shapes file. Section 6.4 lists individuals in a table per class (Individual, Type, Label, Definition). Section 6.6 holds turtle-spec blocks, hidden or not, for what the grammar does not carry. Today that is four property chains and four owl:AllDifferent axioms.

Markers

Regions open with <!-- start: {...} --> and close with <!-- end -->, which closes the innermost open region. A hidden block is one comment wrapped around a fence, <!-- hidden or <!-- hidden: {...}, closed by -->. Keys are exclude (boolean), output-file (a path in the module) and generated (the name of a generated region). Unknown keys are errors. A marker inside any fenced block is text. The extractor refuses a hidden block with both output-file forms, a hidden block containing -->, and a hidden mermaid block.

OD6, the Eligibility pilot

Scope.

  1. The migration check (OD-D33). tools/literate_migration_check.py and mise run check:literate-migration -- <module> <git ref>. For every file the module’s catalogue entry says its README generates, it parses the file in the working tree and at the ref and compares them with rdflib.compare.isomorphic, reporting each difference as triples only in one or the other. A listed reconciliation, a file of expected differences beside the module’s Validation Pack, turns a difference into a pass. It is reused by every later migration.
  2. Enumeration in the grammar (OD-D34). Manchester’s { a, b } in the parser:
    • individuals give [ a owl:Class ; owl:oneOf ( a b ) ], so **Equivalent to.** { ex:One, ex:Two } states an enumerated class
    • literals give [ a rdfs:Datatype ; owl:oneOf ( ... ) ]
    • only { a, b } maps to sh:in ( a b ) in SHACL
    • the Axiom Index writes it back as { a, b }, and the diagram as “one of a, b”
    • comma splitting in labels respects braces as it respects parentheses

    This removes oneOf from the unplanned backlog.

  3. The migration of ontology/eligibility/README.md into the 13 sections:
    • §2 and §3: the header, prefix and contributors tables (OD-D36), and the catalogue entry in §3.
    • Overview: today’s Core Model introduction, with the generated class diagram replacing the hand-drawn one.
    • Detailed Design: today’s Strategy Algebra, the parts of the Core Model and the closures as subsections.
    • §6: every class and property as an entry, the restriction tables (the two sh:in rows checked in SHACL only), and L1 to L8 in a 6.4 table. L9 onwards, and anything else the grammar cannot state, go in 6.6 blocks (OD-D35).
    • Shapes: constraints and rules as hidden blocks that name their files, and structural generated.
    • Canonicalisation, Formalisation (its isabelle-spec block), Dependencies, Release Notes and Open Issues follow.
    • Release notes are rewritten to say what changed and cite ADRs, with no slice references.
  4. Versions (OD-D43). No bump on this branch. Eligibility’s documents change without new version IRIs, and check:ontology-versioning reports them until the release slice OD-REL. The 32 terms with no definition gain one each (OD-D42), drafted from the README and reviewed by the maintainer.

Validation.

  • Existing tests: Eligibility’s README test, the freshness check (its Kernel), the reference semantics and the example tests pass unchanged.
  • New tests: grammar tests for enumeration (OWL classes and data ranges, SHACL sh:in, the views, the refusals), and tests of the migration check (an identical graph passes, a changed triple fails naming it, a listed reconciliation passes).

RC3, the rest of the catalogue

Scope.

  1. The root file’s other blocks.
    • roots: each root, what it owns and its ADRs
    • tools: each tool package’s path, import name and the paths it reaches outside its own tree
    • docs: the documentation areas
    • generated: generated outputs marked so no check depends on them

    The reader and its schema take them.

  2. AGENTS.md’s table (OD-D40). “Where things are” is generated from roots by build:agent-guidance, with its columns unchanged, and check:agent-guidance fails when it is stale.
  3. The bypass scan, report-only. It flags Python under tools/ that builds a path to a catalogued root itself. Known exceptions are listed with a reason each, in a list that may only shrink. The list is a text file beside the reader, with one technical debt row giving its count, which the scan checks (OD-D41).

Validation.

  • The schema: refusals for the new blocks.
  • The generated table: equal to today’s table, and failing when stale.
  • The scan: a planted bypass found, an exception listed, a fixed exception failing until removed from the list, and a technical debt row whose count is wrong failing.

Not covered. The scan failing rather than reporting, which comes once tools have moved. Downstream extension (RC4).

Validation

  • No migration changes meaning. Each migrated layer’s generated graph is isomorphic to its current one (rdflib.compare), except for listed reconciliations the maintainer approves.
  • No output change before migration. OD1 to OD5 leave every current README’s extraction byte for byte unchanged.
  • Determinism. Extraction is idempotent, and the output does not depend on the order of entries in a README.
  • Negative cases first. Each slice’s tests include refusals: an unknown label or key, an unterminated region, a nested expression asserted in SHACL, a hidden block holding -->, a contract that disagrees with the tree, a citation of an unpublished ADR or a developer document.
  • Non-weakening. The per-layer --check tests are kept until RC2 replaces their arguments, and then test the same property.
  • Commands. Every command runs through mise, for example mise exec -- python -m pytest tools/test_literate_extract.py. Each Validation Pack gives its one command and what a pass looks like.
