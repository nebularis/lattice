Persistence: history, versions and the receipt models (sketch)

Unit: formal-methods-track-h, the patch-log half of H2.6b and H2.10, held for this sketch on 2026-10-14 (H-D33) Status: draft for the maintainer, 2026-10-14. Questions VH-Q1 to VH-Q7 are open. VH-Q7 researched 2026-10-14 (§6.1). §9 cross-references the placement vision papers, 2026-10-14 Touches: Foundation’s versioning, Behaviour’s runtime records, Wording’s references by identity (ADR-A112 addendum), the bi-temporal model (ADR-A67), the receipt models of guide Chapter 20 and the persistence README §7.4, aggregate ownership (ADR-A122), TD-42, TD-46, TD-47, TD-48

1. Why this sketch exists

Planning H2.6b’s patch log, the maintainer asked how deep a patch must track a change, using a broker’s tower and a carrier’s requote as the case. Working it through showed that persistence keeps history with a mechanism of its own, the receipt models, which never refers to the versioning Foundation already defines, and that the two disagree. This sketch sets out the facts, the use cases, and the options, and proposes what persistence should do with history. It decides nothing.

2. The scene, checked against the source on 2026-10-14

  1. Foundation versions things. fnd:Version is a mixin. The individual is the version, carries one fnd:hasIdentity, and is followed by its successor through fnd:supersededBy. A version is never edited (the architecture skill’s “identity and versions” principle).
  2. Wording references by identity, and the root fixes the version (ADR-A112 addendum, points 1 and 2). A clause names the identity of what it mentions, and the assembled wording’s wrd:includes lists the versions in force. The property-endorsement example reuses the unchanged ex:sec-2 in wording-v2 and adds only cl-2-1-v2.
  3. Behaviour versions its configuration and never its runtime records. State spaces, transitions and operational profiles are fnd:Version subclasses. Runtime records are immutable individuals, evidenced and temporally scoped, and “records are never reopened” (nested-states sketch §4). A state occupancy names its subject’s persistent identity, “so the state outlives a new version” (ADR-A106 decision 5). An allowance account is one functional balance per record, and the ordered-draws example writes a new account record per change, chained by prov:wasDerivedFrom, with no shared identity.
  4. ADR-A67 forbids in-place correction of runtime data. A correction is a new version superseding the old, which stays queryable. Transaction time is stated per assertion graph.
  5. Persistence knows nothing of versions. Nothing under ontology/persistence names fnd:Version, and the ontology imports nothing. A write to a composite aggregate sweeps the owned closure and writes the caller’s new state (README §7.1). The receipt models record history beside the data: receipt only, patch log, snapshot (README §7.4). The validator requires a patch log for every composite family.
  6. So the two conflict. If a versioned node is inside an owned closure, a replace that writes its new version deletes the old one, against point 4, unless the caller resends every old version on every write.
  7. The workload note already assumes versions are kept in the payload. Its medium programme counts 8 layers, 15 carriers per layer and 2.5 indication versions per carrier at 80 triples a version, 24,400 triples (workload modelling §5.2).

The first three are domain facts and belong to the layers that state them. When they are append-only, the payload never loses a fact, so a patch log or a snapshot of it duplicates them. What a storage log adds is transaction history for data that is edited in place, change capture for downstream consumers, and an audit of what each commit did.

4. How deep a change goes

A triple-level log never needs the path from the root. A triple names its own subject, and replay is set arithmetic. Depth shows up through four other things, which are the real design dimensions.

Dimension Effect on the cost of one change
whether node IRIs survive a write a re-minted subgraph makes every triple look changed
whether the change is an edit or a new thing in law a requote is a new offer, so editing it in place loses a fact
whether a reference pins a version or names an identity pinning forces a new version of every node on the path, as git rewrites trees
how finely versioned nodes are cut a version is copied whole, so a coarse node is copied for one value

4.1 The requote, four ways

The path is tower, layer, quote, terms, premium. A quote version is 80 triples (the workload note’s figure), and the premium is one value on the terms.

Way Written per requote History per requote Current read As-of read
A. edit the premium in place, patch log 1 removed, 1 added, receipt 2 in the log direct backward replay (TD-48)
B. rebuild the quote with new IRIs inside the tower’s aggregate, patch log the tower swept and rewritten 160 in the log direct backward replay
C. a new quote version pinning new member versions about 80, nothing removed in the data follow the current pointer the version current at t
D. a new version of the smallest versioned node, members named by identity, the root’s manifest fixing versions the changed node plus one manifest entry per member in the data resolve through the manifest the manifest current at t

B is what the composite strategy does today if the quote sits in the tower’s aggregate. No new nodes are created. The whole tower is deleted and written back. A medium programme’s tower holds about 9,600 quote triples (8 layers, 15 carriers, 80 triples), so a one-value change rewrites about 19,200 triples (9,600 out, 9,600 back), and TD-42’s quadratic sweep makes that roughly 92 million template fills today. C, with the quote in its own aggregate, adds one quote version of about 80 triples and touches nothing else. A writes 2. Clarified 2026-10-14: an earlier wording read as if the 19,000 were new nodes under C.

4.2 Where the quote belongs

The maintainer’s answer, 2026-10-14. The quote’s versions and history are not part of the tower’s aggregate. A NegotiationThread aggregate, not yet defined, references the tower and governs the quotes. A quote attaches to the layer it is for, though the carrier knows nothing of layers, a broking construct, and quotes only against an attachment point and a limit. A quote is structurally a contract, an instrument on ins:, with a different epistemic status: an indication, a quote, a binding offer, firming as its details build up. This matches the computable-contract-substrate sketch’s account of proposals “at different levels of commitment”, checked by the same shapes as a contract.

So in the worked case the tower is written rarely, the thread is written per move, and each firming or requote is a new quote version. Defining the thread and the quote’s status is domain modelling for another unit (§7).

5.6 Retention (VH-Q6)

Superseded versions are kept until a policy prunes them, which is housekeeping (ADR-A80, TD-47). The questions are where the policy is declared, per family or per class, and whether a version that something still references by version, an assembled wording’s includes for example, may be pruned at all. Leaning: never prune a version a retained version references, the version-level form of the guide’s pinned heads.

6. Behaviour’s versioning (VH-Q7)

The maintainer suspects Behaviour’s different approach has a reason, to be researched. What the source shows:

Behaviour holds How Reading
configuration: state spaces, transitions, profiles fnd:Version things that change by being edited and restated, so versions
runtime records: occupancies, executions, findings immutable individuals, never reopened, temporally scoped and evidenced each is an occurrence, not a state of a continuant, so nothing to version
occasion occupancies derived artefacts, prov:wasDerivedFrom their read set (law B1) derived, so provenance, not succession
allowance accounts a new record per change, prov:wasDerivedFrom the last and the execution, no shared identity the odd one out: a balance is a state of a continuant, the account

6.1 Research, 2026-10-14

Sources read: ADR-A08 (the four tiers), ADR-A92 (derived artefacts), ADR-A106 decision 5, the nested-states sketch §4, the evaluation-context sketch §5, §8 and §9 (unplanned since 2026-10-02), the examples ordered-draws.ttl and sequential-allowance.ttl, and bhv:AllowanceAccountShape.

Finding 1. Behaviour has three disciplines, and each has a reason.

Discipline Behaviour’s members Why not versions
authored and edited, so versions configuration it is what versions are for
something that happened, so an immutable record stimuli, executions, act and exercise records, state occupancies an occurrence has no later state. A resumed state is a new occupancy, never a reopened one (nested-states §4)
computed from records, so a derived artefact occasion occupancies (law B1), and in practice the allowance balances a judgement is evaluated from facts, never authored (AGENTS.md, “Modelling”). Its provenance is its read set, which can span several accounts

Finding 2. A balance is computed state, and its order is the stimulus log’s. The evaluation-context sketch makes the ledger at position p + 1 a function of the ledger at p and the pass at p + 1 (§8), positions come from the stimulus log because the engine never reads a clock (law B3), and the Datalog form is balance(Account, V, p) (§9). A sequential pass adds micro-positions (p, i) in priority order. So a balance record is keyed by its account and its position, and the log order already orders it. Because positions are log order, which only grows, a late stimulus takes a later position, and the balance at an earlier position is never recomputed. That is why no succession link is needed (a hypothesis, holding while law B3 and the evaluation-context design stand).

Finding 3. prov:wasDerivedFrom carries what fnd:supersededBy cannot. In ordered-draws.ttl the alert draw’s guard reads the seat bundle as the seat draw left it, so alerts-1 derives from alerts-0, from the execution and from bundle-2, another account. Succession links one identity’s states. A read set crosses identities.

flowchart LR
  B1["bundle-1<br/>seats 2"] --> B2["bundle-2<br/>seats 1"]
  X2["seat draw, pass 2"] --> B2
  A0["alerts-0<br/>quota 3"] --> A1["alerts-1<br/>quota 2"]
  B2 -- "the guard read it" --> A1
  XA["alert draw, pass 2"] --> A1

Arrows are prov:wasDerivedFrom, from source to derived record. Under versions, bundle-2 would succeed bundle-1 and alerts-1 would succeed alerts-0, and the edge from bundle-2 to alerts-1, the reason the alert fired, would have nowhere to go.

Finding 4. The account record is under-keyed. Three gaps, each a gap between a stated design and the model:

  1. bhv:AllowanceAccount is not typed fnd:DerivedArtefact, although its examples treat it as one and occasion occupancies are (B1).
  2. A record names no owner and no position. The shape requires only bhv:tracksAllowance and bhv:availableBalance. The evaluation-context sketch says a ledger belongs to a persistent identity, as regime state does (ADR-A106 decision 5). Two licences on one allowance definition write records nobody can tell apart, and “current” can be read only from fnd:recordedAt, which is recording time, not the log position.
  3. The name AllowanceAccount is used for a balance at a position. The account itself, the thing with an identity, has no node. The evaluation-context sketch’s EC-Q2, whether allowances become ledger accounts, is the open question that would settle this.

The balances in the examples are blank nodes. Persistence writes no blank node (guide Chapter 5), so a balance quantity needs a minted IRI before it is stored.

6.2 Options, revised

Option Says Consequences
(a) keep the three disciplines, and key the balance state the disciplines in Behaviour’s README. A balance record is a fnd:DerivedArtefact, names its account’s owner (a persistent identity) and its position, and keeps its read set in prov:wasDerivedFrom. Current is the record at the greatest position matches the evaluation-context sketch and B3. About 2 more triples a record (owner, position). Each draw writes one record, append-only, so persistence writes it as a record-append family. A breaking change to Behaviour (ADR-A113), smaller if EC-Q2 decides it
(b) the balance becomes versions of an account identity fnd:hasIdentity and fnd:supersededBy per record loses the cross-account read set unless prov:wasDerivedFrom is kept too. Treats a computed value as authored, against the modelling rule. Within one pass, succession repeats the micro-position order
(c) both allowed, since fnd:Version and fnd:DerivedArtefact are not disjoint succession duplicates the position order at 2 triples a record, and invites a reader to edit a computed value as a version

Leaning (a), revised by §6.4. Behaviour is right to differ: what persistence calls “versioning” is one of three disciplines, and the sketch’s §5 should be read as “a versioned family” for the first, “a record family” for the other two. Finding 4 is input to EC-Q2, not a change this sketch makes.

What this changes.

  1. Behaviour should not change in Track H. The account’s identity and keying (finding 4) is EC-Q2’s to decide, and EC-Q2 comes back at CCS C12 and AIR Phase 5, where capacity’s Phase 0 needs the same answer. Changing bhv:AllowanceAccount here would pre-empt both. Our finding 4 is input to EC-Q2, not a change of our own.
  2. The word “account” is open. The evaluation-context sketch says “ledger account”, capacity says “resource” with an “account”, and the maintainer asks for a less domain-bearing word. That choice belongs with EC-Q2 too.
  3. The three disciplines are confirmed across the roadmap. AIR-6.1 versions its submission, records its approaches, and derives its information gaps. Capacity versions its dependencies and rules, records its demands and draws, and projects a current balance.
  4. Two balance forms coexist, by design. Behaviour’s records hold the history, and capacity’s capx:ExecutableBalance is the current value for the hot path, which is ADR-A67’s two-path split. The projection is an in-place family. Its capx:balanceVersion is an optimistic-concurrency token of its own, which a persistence profile’s version row already provides. That is input to VH-Q5.
  5. VH-Q2 needs a refinement. References by identity hold inside content (ADR-A112), but a record that must cite exactly what it saw pins a version: the assembled wording pins its elements, and AIR-6.1’s submission pins its exposure set. So the rule is “by identity inside content, pinned at the root and wherever a record is evidence of what was seen”.
  6. CCS C16b is where “point, do not copy” is already decided for generated meaning (TD-19). VH-Q2 should cite it rather than restate it.
  7. TD-20 and VH-Q3 touch the same term. A Foundation unit renaming fnd:Version is the natural moment for any change VH-Q3 makes that touches Foundation, and the reason VH-Q3 leans away from importing Foundation into persistence.

6.3 What this changes for persistence

Persistence needs three write disciplines, not two, which VH-Q4 and VH-Q5 should name:

Discipline Persistence write History
versions append a version, move the identity’s current pointer (VH-Q4) in the data
records, occurrences and derived artefacts append only, never replace, keyed by what they are about and their position in the data. Derived records can be regenerated from the records they derive from, so retention may treat them as a cache
in place replace, as today a storage log, if wanted (VH-Q5)

  • The in-force question, which ADR-A67 and the instrument layer answer.

Four places where LATTICE departs from the papers, each a hypothesis the examples should test:

  1. State is read, not authored. The papers keep a thread state, a quote status, a binding status and a fulfilment status side by side. LATTICE evaluates state from acts and records, so four stored statuses become one derivation and cannot disagree.
  2. Binding points, it does not copy. See the table.
  3. Versioning is chosen per family, not applied to every entity, by the three disciplines of §6.3.
  4. History of the words lives in the words. Wording’s amendments are the domain-level patch log the papers built as delta facts.
