A published client SDK for the generated persistence operations (sketch)

Status: early sketch, 2026-10-10. Held for discussion at the end of Track H. Nothing here is planned Raised by: H2-Q1 of the typed IR sketch, which chose PL-B for the typed payload and kept PL-D, generated code per language, for later Related: ADR-A79, ADR-A84 (the minting libraries, the nearest precedent), ADR-A122, the tools/persistence README

1. The scene

After H2, a caller that runs the generated SPARQL without the Python package must do, by hand, every step the README lists:

  • bind each declared parameter with the right datatype
  • build the payload as ground N-Triples, compute the request digest from the same lines, and run the payload-check query over it (typed IR sketch §4.2)
  • mint identities from the recipes (already a library, ADR-A84)
  • run bootstrap-version-row where the profile needs it, confirm every write by reading the transaction claim, classify the outcome, and resend on a transport failure with the same $txnId

Each is a place a caller in another language can go wrong, and none can be checked by the store. An SDK would do them once per language, generated or written against the compiled profile’s declarations (typed IR sketch §3.1, H2-Q5 and H2-Q6).

2. What an SDK would hold

Part Source of truth Generated or written
one typed function per generated operation, with the operation’s parameters as typed arguments the parameter declarations generated
a payload builder per aggregate shape, which can only produce triples the boundary shape reaches from the root the boundary shape and the payload contract generated
the payload check, the digest and the canonical N-Triples the payload contract written once per language
outcome classification after the confirmation read (applied, conflict, refused, unknown) the patterns guide §15.2, and later H6’s Outcomes.thy written, or generated from the theory
retry on an unknown outcome, with the same transaction id and payload the guide written
the store call itself the adopter’s SPARQL client not ours. The SDK takes a minimal interface the adopter implements

3. Options to discuss later

Option Shape Consequences
S-A, a runtime library per language, with nothing generated the written parts of §2, which read the compiled profile at start-up small to build. No typed function per operation, so a misspelt parameter is a run-time error
S-B, S-A plus generated bindings S-A, and a generator that emits the typed functions and payload builders per profile the PL-D of the typed IR sketch. Typed at compile time in the caller’s language. Needs a regeneration step on every profile or shape change, which an adopter must put in their build
S-C, one core with thin bindings the written parts in one language, compiled to WebAssembly or a native library, with thin bindings per language one implementation of the subtle parts. Harder to embed, and it adds a native or Wasm runtime to an adopter’s stack, which ADR-A84 decision 2 avoided for minting
S-D, the core extracted from proofs the outcome classification and payload check from Isabelle, through export_code to Haskell and Scala (FM-D10) the strongest assurance for the parts it covers. Covers two languages, and the rest would still be S-A or S-B

Conformance would follow ADR-A84 decision 5. Vectors in contracts/ (operations, payloads, outcomes), generated by the compiler and checked against independent tools, define conformance. An SDK written from the specification alone conforms on the same terms.

4. Questions to answer before planning

  1. Which languages first. ADR-A84 chose Python and Java for minting, and the same pair would let one adopter use both libraries together.
  2. Whether the SDK reads the compiled profile (RDF) or an exported JSON contract, as minting reads recipes rather than the configuration graph (ADR-A84 decision 3). The latter keeps an RDF parser out of the SDK.
  3. Whether one SDK also serves a relational realisation, if that is ever built. The logical operation contract of H2-Q6 is what would allow it.
  4. Where it lives. packages/ is the home for embedded libraries (ADR-A84 decision 1), but a new package there still needs its own ADR.
  5. Whether it waits for H6’s Outcomes.thy, so the outcome classification is extracted, not written.

5. Why not now

H2 delivers the declarations an SDK would read, and H5 and H6 settle the outcome model it would encode. Building it before them would fix an interface that both may change.
