R0 on Oxigraph

R0 is right wherever it finishes: the replace leaves exactly the payload, the bystander aggregate and references untouched, and the row at the next sequence, at M = N of 10, 100, 1000 and 3000 on both engines, and the six modules above pass on Oxigraph. So the plan’s stop condition, R0 wrong and not slow, did not arise. R0 is superlinear in memory on Oxigraph, which the plan did not anticipate.

Run on 2026-10-12, Python 3.14.8, rdflib 7.6.0, pyoxigraph 0.5.11, a Linux x86_64 container with 15 GB, each run capped at 8 GB, guards off. At 10,000 Oxigraph’s DeleteInsertIter collects the M x N quads in a Vec and an allocation of 7 GB failed under the cap. An earlier uncapped run was killed by the container at 14 GB. Measured separately, a run at 2000 used 1.5 GB and at 4000 used 5.8 GB, so memory is quadratic and 10,000 would need about 36 GB. Timings vary between runs of one machine (Oxigraph at 1000 took 0.56 to 1.9 s), which is why the check does not fail on time.

Decisions needing confirmation

  1. Decided 2026-10-13: option D, built in H2.5. The parameter guard’s datatype test cannot pass on Oxigraph (P5, TD-45). Oxigraph stores any integer-derived literal as xsd:integer and DATATYPE reports it, in every expression and at any parse. So DATATYPE($epoch) = xsd:long, which ADR-A123’s addendum names, is false for every request there, and an operation with the guard on writes nothing on Oxigraph. Every position there is an xsd:integer, so requests and stored rows still match each other, and the integer-versus-long hazard the test guards against cannot arise. I did not change the guard. The Oxigraph runs of the behaviour tests use the guards off (engines.guards()), and the tests about the guard itself run on rdflib only. Options:

    Option Consequence
    A. Leave it. Document that a deployment on Oxigraph runs --no-parameter-guards Nothing to build. That deployment loses the protection against a missing or mistyped parameter, which is the guard’s main value and does not depend on the datatype
    B. Choose the datatype test by what the store keeps. An option on instantiate now (and on compile, recorded in the profile, from H2.7): exact as today, or integer, which tests DATATYPE($p) = xsd:integer and so accepts any integer-derived literal Oxigraph keeps its guard, minus the long-versus-integer distinction it cannot make anyway. A second value of an option to maintain, and H5’s capability record gets a field (whether a store keeps numeric datatypes)
    C. Weaken the test everywhere to isNumeric($p) for Long and Position One form that runs on both. On a store that keeps datatypes it no longer catches an xsd:integer epoch, which a template that only writes the epoch (bootstrap, create) would store

    My leaning was B. The maintainer chose a fourth option, D, on 2026-10-13: a self-calibrating test, DATATYPE($p) = DATATYPE("0"^^xsd:long), which compares the parameter’s datatype with what the store makes of an xsd:long constant. On rdflib only xsd:long passes, exactly today’s guard. On Oxigraph any integer-derived literal passes, which is harmless there since all of them become xsd:integer. A missing or non-numeric value is refused on both, and no option or capability field is needed. Measured on both engines on 2026-10-13 against xsd:long, xsd:integer, a plain integer, xsd:int, a string and an unbound parameter. It assumes a store treats a constant, a parameter and a stored value alike, which P5 is extended to assert. Recorded as ADR-A123’s fourth addendum, and built in H2.5.

  2. R0 needs memory quadratic in the aggregate on Oxigraph (TD-42’s row has the figures). The record of the plan is that H5 selects R2 (one operation, linear) by snapshotUpdateSemantics. P1 now says R2 is unsafe on Oxigraph (it applies in turn) and safe on rdflib, which is the reverse of what the sketch assumed. R1 (two operations in one request) is safe on Oxigraph (P2) and not on rdflib. So no single linear form fits both engines, which is what the capability record is for. Nothing is built here, per the plan.
  3. The oxigraph cases are in check:persistence where the package is installed. bootstrap does not install it (ADR-A125 decision 4), so CI skips them, and check:persistence-oxigraph installs it and runs only them. A developer who ran bootstrap:testing-oxigraph sees them in check:persistence too.
  4. The benchmark’s 10,000 point never finishes on Oxigraph, so it records “did not finish”. Each run is a child process under a memory cap (default 8 GB, COMPOSITE_COST_MEMORY_GB), a run that dies without a result is recorded with its exit status, and that is not a wrong result. The check still fails on a wrong result. If you would rather it fail on an engine that cannot finish, say so.
