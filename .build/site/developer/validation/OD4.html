Validation Pack: OD4, section 6 to SHACL

Unit: improved-ontology-documentation, slice OD4 (plan). Implements: ADR-A126 decision 5, the SHACL half. Built autonomously, at the maintainer’s request of 2026-10-18, with the four design leanings the maintainer agreed that day. The further decisions taken alone are listed below, for the maintainer to keep or overrule.

Invariant

Every restriction row checked in SHACL (Asserted in blank or SHACL) appears in the module’s generated shapes/structural.ttl as the SHACL its flat form maps to, under one shape for its class. A row asserted in OWL alone writes no shape. A nested expression checked in SHACL, a constraint stated twice for one property shape, and a hand-written shape block that names no file or names the generated file are refused. A README not in the layout extracts as before.

The four agreed leanings, as built

  1. Generated SHACL lands in shapes/structural.ttl, generated whole. Hand-written shapes go in section 7 blocks for other files.
  2. One <Class>Shape per class, named by appending Shape to the class’s CURIE, as Eligibility’s are.
  3. Property shapes are blank nodes, with no sh:severity (so each is a violation) and the row’s message.
  4. Versioning is unchanged. A change to the generated file bumps the shapes directory’s .version, as any shape change does.

What changed

  • tools/literate_grammar.py:
    • shacl_constraints() maps one row’s flat form to SHACL.
    • structural_shapes() writes the shapes file, sorted.
    • compile_layout() now returns a Compiled, holding the documents’ openings and the generated shapes.
  • tools/literate_extract.py. plan() writes the generated shapes file, and refuses a shape block of a migrated README that names no file or names the generated one. main() passes both on.
  • tools/test_literate_grammar.py. Tests OD4-T1 to OD4-T7, and the extract helper takes the generated shapes.
  • docs/architecture/literate-specifications.md. The restriction section describes the shapes as built.

Decisions taken alone, for the maintainer

  1. Rows for one property with the same message, or none, share one property shape. Eligibility writes [ sh:path elg:negated ; sh:maxCount 1 ; sh:datatype xsd:boolean ] from what are two rows (max 1, only xsd:boolean), so merging keeps a migrated graph the same. Two such rows that state the same constraint, for example two sh:maxCount, are refused, and a different message gives a row its own shape.
  2. only maps to sh:datatype when its filler is an xsd: datatype, rdfs:Literal or rdf:langString, and to sh:class otherwise.
  3. some C maps to a qualified shape with sh:qualifiedMinCount 1, and value v to sh:hasValue.
  4. In a migrated README every shape block names its file. A positional shape block would otherwise take the generated file’s place in the catalogue’s contract. The catalogue entry still lists shapes/structural.ttl, so RC1-T3 holds the declared and generated files equal.
  5. No structural file is generated when no row is checked in SHACL.
  6. Not supported in the table: a severity other than violation (Behaviour has one sh:Warning shape), SPARQL constraints, and constraints on a property path rather than a property. Those shapes stay hand-written in section 7.
